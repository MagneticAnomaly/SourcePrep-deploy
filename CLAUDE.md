## Dogfooding: You Are Using What You Are Building

This is the RunPrep repository. RunPrep is an MCP tool designed to augment Claude Code (and other AI agents) with deeper structural and semantic understanding of codebases. **You have RunPrep MCP tools available to you right now.** This file and AGENTS.md work together — CLAUDE.md gives you static project knowledge, while the RunPrep MCP tools give you live, queryable access to the code graph, semantic search, dependency analysis, and codebase health metrics.

**Use both.** CLAUDE.md is not a replacement for RunPrep, and RunPrep is not a replacement for CLAUDE.md. Call `prep` at the start of tasks for structural context. Call `prep_search` instead of grep when you need to understand how code connects. Call `prep_impact` before modifying hub files. The AGENTS.md file (auto-generated by RunPrep) documents the available tools and how to call them.

**Critically evaluate RunPrep results.** Because we are dogfooding, every time you use a RunPrep tool, you are also testing the product. If a tool returns unhelpful, incomplete, or misleading results, flag it — that's a bug or improvement opportunity for the product itself. Note when results are surprisingly good too. This continuous feedback loop is essential to development.

## What is RunPrep?

RunPrep is a local-first codebase intelligence platform — prep the context before any AI call. It builds persistent semantic indexes of codebases and serves bounded, source-cited context to AI coding agents via MCP (Model Context Protocol). The goal is to give AI agents robust contextual and epistemological knowledge of a codebase — far beyond what static files or grep can provide. It supports Cursor, Windsurf, Claude Code, VS Code, Gemini CLI, Qwen Code, and GitHub Copilot.

## Architecture

Three-language monorepo: Python backend, Rust performance engine, TypeScript frontends.

### Python Backend (`src/prep/`)

- **Entry points:** `cli.py` (Typer CLI), `server.py` (FastAPI on :8400), `mcp_direct.py` (MCP server)
- **`core/`** — Core engine: indexing, embeddings, file watching, LLM coordination, trace graph, audit system, atlas generation
- **`services/`** — Higher-level orchestration: build pipeline, embedder, augmenter, epistemic enrichment
- **`api/routers/`** — FastAPI routes: projects, search, context, trace, LLM, build, audit, pipeline, roadmap
- **`adapters/`** — Integration adapters
- **`mcp/`** — MCP protocol implementation; `mcp_tools.py` defines all MCP tool handlers
- **`dashboard/`** — React dashboard app (lives inside Python package but is a separate npm workspace)

### Rust Engine (`engine/crates/`)

Called from Python via `maturin` bindings. Workspace crates:
- **prep-engine** — Main orchestrator
- **prep-walker** — File system traversal
- **prep-parser** — AST parsing via tree-sitter (Python, TypeScript)
- **prep-graph** — Symbol graph building (nodes, edges, import chains)
- **prep-chunking** — Code segmentation for embeddings
- **prep-sanitize** — Content filtering
- **prep-selfheal** — Error recovery

### Frontend (`packages/`, `src/prep/dashboard/`, `websites/`)

npm workspaces managed by Turbo:
- **`packages/ui`** — Shared React component library (`@prep/ui`). Tailwind + Radix UI + Tremor charts. Storybook for design system docs.
- **`src/prep/dashboard`** — Main dashboard app (React/Vite, optional Tauri wrapper). Connects to daemon API at :8400.
- **`packages/vscode`** — VS Code extension with webview UI
- **`websites/apps/*`** — Marketing and docs sites (Next.js)

### Data Flow

1. **Indexing:** Rust engine parses files (tree-sitter) into a structural graph → Python enriches with embeddings (ONNX native or Ollama) and optional LLM augmentation (multi-pass pipeline)
2. **Storage:** SQLite for project registry, JSON files + numpy arrays for indexes. Standalone mode in `~/.local/share/runprep/projects/`, embedded mode in `.runprep/` (git-trackable)
3. **Serving:** FastAPI daemon exposes search/context/trace APIs. MCP server wraps these for IDE consumption. Dashboard talks to the same HTTP API.

## Code Style

## Daemon State Location

Phase 113 consolidated daemon-wide state (SQLite stores, ui_config,
registry, audit log) into a single canonical location. Pre-Phase-113
installs had state split between `./prep_data/` (CWD-relative) and
`~/.local/share/runprep/` (XDG).

| Env state | Location |
|---|---|
| `$PREP_DATA_DIR` set (must be absolute) | `$PREP_DATA_DIR` |
| Default | `~/.local/share/runprep/` |

Legacy `./prep_data/` is auto-migrated on first daemon startup
(see `src/prep/core/data_dir_migration.py`). Sentinel file
`<data_dir>/.migrated_from_cwd` records the migration and prevents
re-runs. Conflicts (both sides non-empty) are resolved with
row-count / size heuristics; losers preserved as
`<name>.migration-conflict.<ISO8601>`.

Per-project indexes (embedded mode's `.runprep/`, standalone mode's
`<data_dir>/projects/<id>/`) are unchanged.

## RunPrep MCP Tools (Use These)

This project ships its own MCP server. See AGENTS.md for tool-calling details and the current project_id. When the RunPrep daemon is running, these tools are available and **should be actively used during development**:

| Tool | When to Use |
|------|-------------|
| `prep` | **START of every task.** Returns structural overview: module map, hub files, focus areas, cross-cutting concerns. Also surfaces immune system alerts (warnings from antibodies). |
| `prep_search` | Find code by meaning, not just string match. **Auto-classifies your query** — "where is X" routes to symbol lookup, "why X" routes to concepts, "who imports X" routes to trace graph. Use the `intent` param to override if needed. |
| `prep_impact` | **BEFORE editing hub files.** Shows blast radius — what depends on a file and what breaks if you change it. Filters stdlib/external noise automatically. |
| `prep_audit` | **Dual-mode tool.** (1) Call with no args for structural findings — coupling hotspots, import cycles, concept violations. (2) Pass `findings=[...]` to enrich external lint results (ruff, eslint, semgrep) with structural context. Accepts SARIF dicts for SARIF-in/SARIF-out enrichment. Use `action="antibodies"` to see immune system defenses. |
| `prep_observe` | Save/retrieve cross-session notes and observations. Observations about decisions or patterns may be promoted to concepts. |
| `prep_concepts` | Record/query business rationale and design decisions. Concepts have testable assertions, anchors to files, and linked documentation. Constraint concepts auto-generate immune system antibodies. |

All RunPrep tools are read-only and safe to auto-approve.

### Audit Enrichment Workflow

When auditing code, use RunPrep to make lint findings smarter:

```
1. Run your linter:    ruff check src/ --output-format json
2. Enrich findings:    prep_audit(findings=[{file, line, message, severity, tool}])
3. RunPrep adds:       dependent count, hub status, related concepts, risk score, recommendation
```

For GitHub Code Scanning / semgrep / CodeQL users, pass SARIF directly:
```
prep_audit(findings={SARIF dict})  →  enriched SARIF with properties.prep on each result
```

### Search Intent Classification

`prep_search` automatically detects what you're asking:

| Query Pattern | Auto-Detected Intent | What Happens |
|--------------|---------------------|-------------|
| "where is X", "find X" | LOCATE | Symbol lookup — returns path, signature, line number |
| "how does X work" | EXPLAIN | Semantic search with trace expansion |
| "why does X use Y" | RATIONALE | Concepts-first, falls back to semantic search |
| "who imports X" | TRACE | Graph traversal via `prep_impact` |
| "example of using X" | EXAMPLE | Semantic search for usage patterns |
| "what's in X directory" | DISCOVER | Module overview with expanded context |

Override with `intent` param if auto-detection gets it wrong: `prep_search(query="...", intent="locate")`

### Immune System (Antibodies)

RunPrep derives runtime defenses from constraint/architecture concepts. When a concept says "Pi Agent must never import LLM libraries", RunPrep creates an antibody that fires when that constraint is violated. Alerts surface in `prep()` ambient context.

- View antibodies: `prep_audit(action="antibodies")`
- Antibodies are derived from concepts with assertions and anchors
- All alerts are informational — nothing is blocked

**Dogfooding note:** Every call to these tools is also a test of the product. If results are unhelpful, incomplete, or wrong, that is actionable product feedback — mention it.

## MCP Server Modes

RunPrep has two MCP server implementations. Understanding the difference prevents confusion:

- **Server mode** (`src/prep/mcp/server.py`, default) — Proxies to the running daemon at :8400. Full-featured: multi-project support, ambient context (atlas, hub files, modules), all 6 tools + aliases, adaptive context budgets per client, role-based atlas projection. **Use this when the daemon is running.**
- **Direct mode** (`src/prep/mcp_direct.py`, `--mode direct`) — Runs CodeIndex/TraceIndex in-process, no daemon required. Simpler single-project setup but has drifted behind server mode. The `prep` no-arg ambient context call is broken in direct mode (routes to search-context which requires a query). Only handles a subset of tools.

The wrapper script (`prep-mcp-wrapper.sh`) and `.claude/mcp.json` / `.cursor/mcp.json` should default to server mode. Direct mode is a valid feature (daemon-free MCP) but needs parity work to match server mode's tool dispatch.

## How RunPrep Generates AGENTS.md for Client Projects

A core RunPrep feature is generating AGENTS.md files that tell AI agents about the MCP tools available to them. Understanding this pipeline is essential when working on the product.

### Generation Pipeline

1. **`src/prep/core/rules_generator.py`** — Main orchestrator. `write_rules_file()` detects target IDEs and dispatches to per-IDE writers. `_build_managed_content()` generates the unified content block shared across all targets (Cursor, Windsurf, Claude Code, Copilot, etc.).
2. **`_write_agents_md()`** (rules_generator.py:760) — Writes to `AGENTS.md` at the client project root. Uses `<!-- prep-managed-start/end -->` markers to splice managed content while preserving user additions.
3. **`src/prep/mcp_tools.py`** — Defines the 6 core MCP tool schemas (name, description, parameters, annotations). These are served via `mcp/server.py` `handle_tools_list()` and are the source of truth for what tools exist.
4. **`src/prep/core/atlas/`** — Generates the "Codebase Atlas" section: project identity, stack summary, workspace map, cross-cutting concerns, hub files.

### What Goes Into a Generated AGENTS.md

- **Tool calling instructions** — Hardcoded in `_build_managed_content()`. Tells agents to call `prep` immediately, routes via `project_id`, maps user intents to tool calls.
- **Codebase Atlas** — Auto-generated structural snapshot: identity, stack, workspace segments, hub files, entry points, import cycles.
- **Focus Areas** — User-selected paths for priority context.
- **Refresh hints** — When to re-call `prep` during long tasks.

### Design Intent

The generated AGENTS.md is meant to be the first thing an AI agent reads when it opens a client project. It declares: "You have an MCP tool — use it to get live structural context beyond what any static file can provide." The tool instructions are front-loaded and aggressive ("IMMEDIATELY call", "No announcements") because the biggest failure mode is agents ignoring the MCP tools and falling back to grep/file reads for everything.
