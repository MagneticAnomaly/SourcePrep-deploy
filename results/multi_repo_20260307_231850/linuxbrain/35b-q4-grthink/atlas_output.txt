IDENTITY: Halley Core is a local-first AI persona system that orchestrates autonomous agents with persistent memory, emotional modeling, and multimodal generation capabilities via a React frontend and Python backend.

STACK: Python 3.8+ with FastAPI and Flask backends, React with TypeScript and Tailwind CSS frontend, Rust Tauri for desktop packaging, Ollama for local LLM inference, ComfyUI and Diffusers for image/video generation, PyTorch for deep learning, and Tailscale for secure remote GPU access.

ARCHITECTURE: The system follows a layered architecture with business logic in Python modules, presentation in React components, and infrastructure for GPU orchestration. The halley_core/api/app.py serves as the central API gateway connecting frontend UI components like halley_core/frontend/vite.config.ts to backend services. The frontend infrastructure relies on React components in halley_core/frontend/components, while the backend uses Flask and FastAPI routes in halley_core/api. The halley_core/frontend directory contains the UI entry points and state management, while halley_core/backend handles inference and memory logic. The system integrates with external providers like RunPod for cloud GPU resources and local Ollama for inference.

FLOW: User interaction begins at the frontend entry point halley_core/frontend/index.tsx, routing through the App component in halley_core/frontend/app.py. User actions trigger API calls to halley_core/api/app.py, which routes to specific handlers like halley_core/api/chat_interface.py. The backend orchestrates LLM inference via halley_core/api/ollama_provider.py or halley_core/api/llm_adapter.py, managing context through halley_core/context/context_assembly.py. Memory operations flow through halley_core/memory/semantic_storage.py, utilizing the retrieval logic in halley_core/retrieval/context_retriever.py. For media generation, requests pass to halley_core/media/central_orchestrator.py, which coordinates with halley_core/images/generation_pipeline.py or halley_core/media/visual_content_orchestrator.py. GPU resources are managed by halley_core/resources/gpu_monitor.py, ensuring VRAM constraints are met. Observability is maintained via halley_core/observability/logger.py and halley_core/observability/metrics.py.

PATTERNS: The system employs a provider pattern for image and video generation, allowing dynamic switching between ComfyUI, Diffusers, and Wan. Dependency injection is used for LLM adapters and GPU services. Error handling follows a resilience pattern with circuit breakers in halley_core/resilience/error_handler.py and automatic retry logic. The frontend uses a component library with Radix UI primitives and Tailwind CSS for consistent styling. State management relies on React hooks and custom hooks like halley_core/frontend/websocket_hook.py for real-time updates.

RISKS: Test scripts contain hardcoded absolute paths and magic numbers limiting portability. The TabbedSelector component casts 'tab' to 'any', indicating type safety gaps. Hardcoded polling intervals cause potential API load, and inconsistent error handling swallows failures. The PersonasDialog component relies on placeholder JSX until UI extraction is complete. Incomplete implementation for ComfyUI image generation provider initialization and partial AMD GPU support exist. The TimmModel adapter has unstable APIs and the IDEncoder relies on dynamic attribute creation. Hardcoded repository paths and model names in PuLID limit portability. CoreML and Mochi video providers are stubbed with explicit errors. The CLIP model infrastructure relies on conditional import fallbacks that degrade performance silently. The model adapter module lacks robust handling for GPT-like models. The useWebSocket hook lacks automatic reconnection logic and has SSR compatibility issues. The Photos page contains stubbed functionality. The subsystem relies on a design specification document for memory analysis rather than an implemented module. The video service contains a TODO to verify model availability. Historical data integrity issues regarding missing vector embeddings required remediation scripts. The error message generation logic contains commented-out code for persona-specific customization. The subsystem suffers from hardcoded API URLs and truncated implementation in the upload handler. The subsystem relies on a legacy JSONL storage format requiring migration. The subsystem maintains a dual-strategy architecture with legacy and V2 budget managers. The subsystem relies on a pinned version of optimum as a workaround for deprecation. The subsystem relies on pending development phases to transition from conceptual specification to implementation. The subsystem suffers from tight coupling due to hardcoded Ollama server IPs and lacks access controls for NSFW content. The subsystem has unresolved 'Halbert' references, unused imports, and lacks comprehensive testing. The regeneration logic in the load method lacks necessary checks to trigger updates.
