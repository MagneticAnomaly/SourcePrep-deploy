IDENTITY: HomeColab is a collaborative real estate search platform for iOS and web that enables agents and clients to share property data, vote on listings, and visualize comparisons through 3D matrices while adhering to strict legal compliance and monetization strategies.
STACK: Languages include Swift, TypeScript, JavaScript, Markdown, and Shell. Frameworks are SwiftUI, React, React Three Fiber, Framer Motion, Next.js 14, and Firebase. Build tools involve Swift Package Manager, Xcode, and Netlify. Runtime environments cover iOS, web browsers, and server-side Node.js.
ARCHITECTURE: The system follows a layered architecture with documentation (282 files), presentation (202 files), business logic (45 files), configuration (20 files), infrastructure (17 files), data (8 files), testing (8 files), and build (5 files). The core entry point is App/HomeColabApp.swift which initializes Firebase and manages the app lifecycle. Business logic is centralized in Managers/FirestoreManager.swift which acts as a monolithic hub for data operations. The presentation layer is split between iOS views like Views/Queue/QueueView.swift and web components in Components/UnifiedListingCard.swift. Data models are defined in HomeColabCore and shared via Swift Packages. The architecture bridges a legacy single-tenant model with a proposed 'Shared Core, Separate Apps' strategy for the Business App.

FLOW: User interaction begins at App/HomeColabApp.swift which initializes Firebase and routes to Views/Queue/QueueView.swift or web landing pages. Data ingestion flows through Ingestion/LinkPreviewManager.swift or Ingestion/Normalization.swift to Managers/FirestoreManager.swift. The FirestoreManager writes to Firestore and triggers Cloud Functions for notifications. Real-time updates are handled by the SyncManager in HomeColabCollaboration. Visualization renders via Spatial/MatrixView.swift or React components in Dashboard/MatrixView.swift. Legal compliance is enforced by Legal/Compliance.swift and Legal/ComplianceRules.swift during data ingestion. Monetization logic in Monetization/AdManager.swift determines ad visibility based on user state.
PATTERNS: The system uses a monolithic FirestoreManager for data operations, violating single responsibility. Dependency injection is partially implemented via Swift Packages for shared logic. Error handling is centralized in Build/AppError.swift but suffers from inconsistent practices. State management relies on a mix of SwiftUI state, Zustand stores for web, and in-memory chat stores. Feature flags are migrating from static Swift constants to Firebase Remote Config.
RISKS: Critical technical debt includes monolithic 'god object' components (FirestoreManager, UnifiedListingCard) violating Single Responsibility. Hardcoded feature flags and missing crash reporting exist. Insecure Firestore rules allow unauthorized updates. The advertising layer lacks GoogleMobileAds SDK integration. Deprecated LinkPresentation framework requires migration to UnifiedListingCard. Potential infinite loops exist in FirestoreManager+Sync due to timestamp mismatches. The current 1:1 user-to-space Firestore model blocks multi-user spaces required for the Business App. Legacy print statements coexist with planned logging migration. Placeholder Ad Unit IDs and incomplete SKAdNetwork identifiers hinder monetization. Documentation contains future-dated timestamps and unresolved placeholders.
