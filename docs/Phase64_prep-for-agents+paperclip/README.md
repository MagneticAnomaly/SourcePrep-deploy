# Phase 64 — Sub-Atlas Architecture: Role-Based Context Routing for Agents

> **Phase 64: Preparing CoDRAG for Paperclip + Multi-Agent Ecosystems**
> Date: 2026-03-30
> Status: Research & Architecture

---

## 1. The Insight

> *"We already have tools to build sub-atlases. If we're building agent files like AGENTS.md, SOUL.md, KNOWLEDGE.md, we could save context by offering a method to link to the atlas or sub-atlas — and build our sub-atlases for different role subcategories (engineering/design/finance/legal/marketing/etc) so each agent can route to the right sub-atlas."*

This is a **context efficiency strategy** that combines CoDRAG's existing segmented atlas architecture with the emerging agent workforce pattern (Paperclip, CrewAI, etc.). The core idea: instead of every agent getting the full ~4000-char atlas, each agent gets a **role-appropriate sub-atlas** that maximizes signal-to-noise ratio for their specific domain.

---

## 2. What Already Exists (CoDRAG's Atlas Stack)

### 2.1 The Current Atlas Hierarchy

CoDRAG already has a complete three-tier atlas system built in `src/codrag/core/atlas/`:

```
┌───────────────────────────────────────────────────────────┐
│  Tier 1: Single Atlas (AtlasDocument)                      │
│  ─────────────────────────────────────                     │
│  • One document, ~1200-4000 chars                          │
│  • Global orientation: IDENTITY, STACK, ARCHITECTURE       │
│  • Generated by: generator.py → generate()                 │
│  • Triggered at: ≥2 files indexed                          │
│  • Stored as: atlas.json in index_dir                      │
│                                                             │
│  Tier 2: Segmented Atlas (Root + SegmentDocuments)          │
│  ────────────────────────────────────────────               │
│  • Root atlas (1200-2500 chars): IDENTITY + WORKSPACE MAP   │
│  • Per-segment atlases (800-1500 chars each)                │
│  • Segments discovered from: workspace boundaries,          │
│    monorepo packages, or adaptive directory depth           │
│  • Generated by: generator.py → generate_segmented()       │
│  • Triggered at: ≥2 segments detected                      │
│  • Stored as: atlas.json (root) + atlas_segments/ dir       │
│                                                             │
│  Tier 3: Segment Routing (SegmentDescriptors + Embeddings)  │
│  ─────────────────────────────────────────────────────────  │
│  • Pre-computed descriptor embeddings per segment            │
│  • Query-time routing via cosine similarity                  │
│  • Selects ≤3 relevant segments per query                    │
│  • Generated by: generator.py → generate_routing()          │
│  • Stored as: atlas_routing.json + atlas_routing_embeddings  │
│  • Activation threshold: ≥20 files AND ≥2 modules           │
└───────────────────────────────────────────────────────────┘
```

### 2.2 Key Data Models (from `atlas/models.py`)

| Model | Purpose | Key Fields |
|---|---|---|
| `AtlasDocument` | Cached full/root atlas | content, fingerprint, mode (llm/structural) |
| `Segment` | Directory-based file grouping | id, dir_path, file_paths, module_ids, domain_tags |
| `SegmentDocument` | Per-segment cached atlas | content, segment_id, segment_name, dir_path |
| `SegmentDescriptor` | Query routing metadata | covers (embedded text), key_files, boundaries |

### 2.3 Current Routing Flow (from `atlas/routing.py`)

```
Query arrives via codrag_search
  → query_vector = embed(query)
  → scores = cosine_sim(query_vector, descriptor_embeddings)
  → top 3 segments with score ≥ 0.25 selected
  → segment atlases loaded and prepended to context
  → score boost (+0.12) for files within selected segments
```

**Bottom line: CoDRAG already has sub-atlases (segments) and a query-routing system (descriptors + embeddings).** What it lacks is **role-based projection** — the ability to serve different *views* of the same codebase to different agents based on their role.

## 3. The Gap: Structural Segments ≠ Role Views

### Current Segments: Directory-Based (Technical)

CoDRAG's segments partition by **directory structure**:
- `src/codrag/core` → "Core Engine" segment
- `packages/ui` → "UI Component Library" segment
- `packages/vscode` → "VS Code Extension" segment

This is optimal for developer-agents doing code modifications. It's **not** optimal for:
- A **design agent** that needs UI patterns, design tokens, and component APIs
- A **marketing agent** that needs product capabilities, pricing features, and competitive positioning
- A **QA agent** that needs test coverage, error handling patterns, and fragile code areas
- A **DevOps agent** that needs build config, deployment scripts, and infrastructure
- A **security agent** that needs auth flows, data handling, and dependency audit

### What Role-Based Sub-Atlases Would Provide

Instead of **territorial** segments (by directory), **functional** projections (by concern):

```
Same Codebase Graph
       │
       ├─→ Engineering Sub-Atlas:  modules, dependencies, architecture, code patterns
       ├─→ Design Sub-Atlas:       component library, design tokens, layout patterns
       ├─→ QA Sub-Atlas:           test coverage, error handling, spaghetti scores
       ├─→ Security Sub-Atlas:     auth flows, data handling, dependency vulnerabilities
       ├─→ DevOps Sub-Atlas:       build system, deployment, CI/CD, infrastructure
       ├─→ Product Sub-Atlas:      features, capabilities, integration points, APIs
       └─→ Custom Sub-Atlas:       user-defined focus areas (already have this!)
```

## 4. Architecture: Role Sub-Atlases as Views

### 4.1 The Key Realization

> **Role sub-atlases are NOT separate indexes.** They are different *projections* of the same graph, filtered and compressed through role-specific lenses.

The data is the same code graph, modules, and epistemic annotations. The *presentation* changes:

```
┌────────────────────────────────────────────────────────┐
│  CoDRAG Core (The Hexagon)                              │
│                                                          │
│  Code Graph ──→ Modules ──→ Epistemic ──→ Atlas Engine  │
│                                                          │
│                         Role Projector                   │
│                              │                           │
│          ┌───────┬───────┬───┴───┬───────┬───────┐      │
│          │       │       │       │       │       │      │
│        Eng.   Design   QA    Security DevOps Product   │
│        View   View    View   View    View   View       │
│                                                          │
│  Each "view" is:                                         │
│    1. A filter: which modules/files are relevant          │
│    2. A prompt lens: what aspects to emphasize            │
│    3. A compression: what detail level to use             │
│    4. A vocabulary: domain-specific terminology           │
└────────────────────────────────────────────────────────┘
```

### 4.2 Implementation Strategy: RoleProjection

```python
@dataclass
class RoleProjection:
    """A role-based view of the codebase atlas."""
    role_id: str           # "engineering" | "design" | "qa" | "security" | etc.
    display_name: str      # "Engineering" | "UX Design" | "Quality Assurance"
    
    # Filter: which files/modules are relevant to this role
    include_layers: List[str]     # e.g. ["api", "service", "data_access"] for engineering
    include_domain_tags: List[str] # e.g. ["ui", "component", "design-system"] for design
    exclude_domain_tags: List[str] # e.g. ["test", "mock"] for non-QA roles
    file_glob_patterns: List[str]  # e.g. ["*.test.*", "*.spec.*"] for QA
    
    # Prompt lens: what to emphasize
    emphasis_sections: List[str]   # Which atlas sections to expand
    suppress_sections: List[str]   # Which atlas sections to minimize
    
    # Agent file mapping: which agent files consume this projection
    agent_files: List[str]         # ["AGENTS.md", ".claude/skills/codrag.md"]
    
    # Compression: how much detail
    max_chars: int = 2000          # Budget for this role's sub-atlas
```

### 5.1 The Agent File Landscape (2026)

Agent configuration files have converged on a pattern:

| File | Purpose | Who Reads It |

| `CLAUDE.md` | Claude Code specific instructions | Claude Code |

| `.windsurf/rules/` | Windsurf-specific rules | Windsurf |
| `GEMINI.md` | Gemini-specific rules | Gemini CLI |

### 5.2 The Integration: Sub-Atlas References in Agent Files

Instead of embedding the full atlas in every agent file (which wastes context), agent files reference the **relevant sub-atlas**:

```markdown
<!-- In a Paperclip agent's KNOWLEDGE.md for a "CTO" agent -->

# CTO Knowledge Catalog

## Codebase Intelligence (via CoDRAG)
- **Full Atlas**: `codrag` (call for complete structural overview)
- **Engineering View**: `codrag --role engineering` (architecture, dependencies, flow)
- **Security View**: `codrag --role security` (auth flows, data handling, risks)

## On-Demand Deep Dives
- Call `codrag_search` for specific code queries
- Call `codrag_impact` before approving architectural changes
- Call `codrag_audit` for health diagnostics
```

```markdown
<!-- In a Paperclip agent's KNOWLEDGE.md for a "UX Designer" agent -->

# UX Designer Knowledge Catalog

## Codebase Intelligence (via CoDRAG)
- **Design View**: `codrag --role design` (component library, design tokens, patterns)
- Call `codrag_search` for component usage patterns
```

### 5.3 How CoDRAG Serves Role-Filtered Context

The `codrag` MCP tool (and CLI) gets a new optional `role` parameter:

```
codrag(role="engineering")     → Returns atlas filtered for engineering concerns
codrag(role="design")          → Returns atlas filtered for design concerns
codrag(role="security")        → Returns atlas filtered for security concerns
codrag()                       → Returns full atlas (current behavior, backward-compatible)
```

Under the hood, this maps to:
1. Load the full atlas (already cached)
2. Apply the `RoleProjection` filter
3. Re-compress using the role's emphasis/suppress rules
4. Return within the role's char budget

## 6. Context Budget Analysis

### 6.1 Current Context Cost

Without role filtering, every agent gets the full atlas:

```
Full atlas:           ~2500-4000 chars
+ Focus areas:        ~300-500 chars
+ Tool instructions:  ~1500 chars
= Per-agent cost:     ~4300-6000 chars

10 Paperclip agents × 6000 chars = 60,000 chars of context per heartbeat cycle
```

### 6.2 With Role-Based Sub-Atlases

```
Role sub-atlas:       ~1000-2000 chars (filtered + compressed)
+ Role-specific tips: ~200 chars
+ Tool instructions:  ~800 chars (trimmed for role)
= Per-agent cost:     ~2000-3000 chars

10 Paperclip agents × 3000 chars = 30,000 chars of context per heartbeat cycle
```

**~50% context savings** while actually improving relevance per agent.

### 6.3 The Real Win: Signal-to-Noise Ratio

A security agent doesn't need to know about the D3.js visualization subsystem. A design agent doesn't need to know about the pipeline orchestrator's state machine. Role filtering eliminates irrelevant context that wastes tokens and can confuse agents.

## 8. Implementation Approach

### Phase 64A: Role Projection Engine (No LLM, Pure Filtering)

1. Define `RoleProjection` dataclass
2. Implement `project_atlas_for_role(atlas_content, role_id)` — filters existing atlas text by section emphasis/suppression
3. Add `role` parameter to `codrag` MCP tool
4. Add `--role` flag to `codrag` CLI
5. Backward-compatible: `role=None` returns full atlas

**Effort: 2-3 days. No pipeline changes. No new LLM calls.**

This is the critical architectural point: role projections don't require re-generating the atlas per role — they *filter and compress* the single existing atlas. This means:
- Zero additional LLM cost
- Zero additional build time
- Instant role switching

### Phase 64B: LLM-Enhanced Role Atlases (Optional, If Needed)

If filtering isn't nuanced enough, add a per-role LLM synthesis step:
1. Feed the full atlas + role projection config to an LLM
2. Generate a role-specific atlas variant
3. Cache alongside segment atlases

**Effort: 3-5 days. One LLM call per role per atlas refresh.**

### Phase 64C: Role-Aware AGENTS.md / KNOWLEDGE.md Generation

1. Extend `rules_generator.py` to accept a `role` parameter
2. When Paperclip agents (or any tool) specify a role, emit role-filtered atlas in their agent file
3. Add `codrag_role` support to KNOWLEDGE.md on-demand catalog pattern

**Effort: 1-2 days.**

### Phase 64D: Custom Role Definitions

1. Allow users to define custom roles via dashboard or `role_projections.json`
2. Custom roles specify their own include/exclude tags, file patterns, and emphasis
3. A company could define: "finance-agent", "compliance-agent", "documentation-agent"

**Effort: 2-3 days.**

## 11. Strategic Context

### Why This Matters for CoDRAG's Market Position

From the Phase 62 Strategic Pivot: CoDRAG is a **Knowledge Provider, not a Project Manager**. Role-based sub-atlases extend this identity:

> *"CoDRAG doesn't just provide codebase intelligence — it provides **role-appropriate** codebase intelligence. A security agent gets security-relevant context. A design agent gets design-relevant context. Same codebase, same graph, different projections."*

This is a genuine differentiator because:
1. No other tool does this — most indexing tools give the same context to every agent
2. It reduces agent confusion (less irrelevant noise)
3. It saves tokens (smaller context per agent = lower cost)
4. It scales naturally with team size (10 agents × 10 roles = still the same underlying data)

### Compatibility with Every Agent Framework

| Framework | How They Consume Role Sub-Atlases |
|---|---|
| **Paperclip** | Agent-level `codrag_role` in adapter config |
| **CrewAI** | Role-specific context in crew agent definitions |
| **LangGraph** | Node-level context injection based on role |
| **Claude Code** | `codrag(role="X")` in CLAUDE.md instructions |
| **Cursor/Windsurf** | Role-filtered atlas in rules files |
| **Pi** | `codrag context --role X` in skill file |
| **Custom A2A** | `role` parameter in task request |

## 12. Open Questions

### Q1: Should role projections combine with segment routing?

Two orthogonal dimensions:
- **Segment** = which part of the codebase (directory/package)
- **Role** = what aspect of the code matters (security/design/engineering)

They could compose: "give me the security view of the auth segment."

### Q2: Who defines roles — CoDRAG or the consuming tool?

Option A: CoDRAG ships built-in roles, users extend via `role_projections.json`
Option B: The consuming tool (Paperclip) passes arbitrary role descriptors, CoDRAG uses LLM to generate appropriate projections

**Recommendation: Option A for now.** Built-in roles with user extensibility. LLM-generated projections are over-engineered for MVP.

### Q3: Should roles influence search scores?

Currently `codrag_search` scores are segment-influenced (ROUTING_SEGMENT_BOOST = 0.12). Should a `role=security` query also boost files tagged with security domain tags?

**Recommendation: Yes, but as Phase 2.** Start with atlas view filtering, add search scoring later.

### Q4: How does this interact with Paperclip context budgets?

Paperclip agents have token budgets. Role sub-atlases help stay within budget. The `max_chars` per role projection should be configurable and should respect the agent's overall context budget.
