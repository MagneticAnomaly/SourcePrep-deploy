# 01 — Cycles as Diagnosis

**Status:** ✅ Feasible. Lowest operational risk of the five. Recommended first experiment.
**Depends on:** `prep_audit` circular dependency detection (`src/prep/core/audit/analyzers/circular_deps.py`, Tarjan's SCC).
**Does not depend on:** LLM enrichment, concepts, antibodies, or any external harness.

## The premise

An import cycle is usually treated as a lint warning. Most developers ignore them or silence the check. But a cycle is a fossil — it preserves a specific moment where a developer chose convenience over separation, and the cycle stayed because nobody could afford to untangle it. Read as archaeology, cycles tell you something true about how a codebase was built.

This essay is a reading of real cycles in real repos.

## The scenario to run

1. Pick 2–3 repos from `tests/eval/real_repos/`. Recommended starting set: **`gin-go`** (Go web framework, well-engineered, should have few cycles), **`sqlmodel-python`** (Python, type-heavy, may have inheritance-induced cycles), **`ripgrep-rust`** (Rust, well-factored, should have close to zero).
2. For each repo, run Prep's full index (structural layer is enough; no LLM enrichment needed for cycle detection).
3. Run `prep_audit` with the structural scan action. Extract the circular dependency findings.
4. For each cycle of interest, `git log` the files involved. When was each file first added? When did the cycle form? Was the cycle there from commit one or did it grow over time?
5. Read the files involved. Not to judge them — to understand them. What was the developer trying to do? Why did convenience win over separation?

## What to record

- Raw `prep_audit` output per repo, verbatim
- Count of cycles per repo, longest cycle length, SCC size distribution
- For each cycle used in the essay: commit SHA where it was introduced, commit message, file list
- Your actual read-through of the files — what did the cycle do for the developer that separating them wouldn't have?

Drop this into `01_cycles_raw_output.md` in the same folder before writing prose.

## What the essay argues

One central claim: **the shape of a cycle reveals the pressure the developer was under**. A cycle between two utility files is different from a cycle between a model and a service is different from a cycle between a web handler and its renderer. Each one is a fingerprint of a specific tradeoff.

The essay tours three real cycles and reads them. Prep is mentioned as the tool that surfaced them, with the honest caveat that any static analyzer can find cycles — what's novel is treating them as text to read instead of warnings to silence.

## Honesty checks — what could go wrong

- **The cycles might be boring.** Utility files circularly importing constants. Autogenerated code. If every cycle in all three repos is junk, the essay becomes "I expected drama and found mostly bookkeeping" — which is itself an honest finding and arguably a better essay than the original pitch.
- **The repos might have zero cycles.** `ripgrep-rust` is well-factored and may be cycle-free. Good. Write that: "here are three repos by experienced maintainers, only one has cycles, here is what is different about that one."
- **Prep might mis-detect cycles.** If the structural parser misreads a dynamic import, the cycle might be spurious. Verify by hand before publishing. If Prep generates false positives, note them as a limitation in the essay.
- **The narrative might be overfitted.** Reading cycles as archaeology is a metaphor. If it doesn't hold up against the actual evidence, don't force it.

## Limitations to acknowledge in the essay

- Prep's cycle detector works at the import level, not at the runtime call-graph level. A cycle it finds is a *static* cycle; a runtime cycle might be invisible to it, and a static cycle might never fire at runtime.
- Go, Python, and Rust handle cycles differently at the language level. Go disallows package cycles entirely; Python permits them at import time (usually); Rust's module system discourages them. The essay should note that what counts as a "cycle" isn't language-neutral.
