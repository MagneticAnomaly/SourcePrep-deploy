# Phase 133b — Dot-Dir Policy Research

> **Scope:** Decide the policy for dot-directories (`.claude/`, `.agents/`,
> `.github/`, `.devcontainer/`, etc.) across two surfaces:
> (1) the **trace pipeline** (what gets indexed as source) and
> (2) the **concept synthesizer** (what gets fed as planning grounding).
>
> **Status:** Research complete; recommendation below; implementation pending.
> **Date:** 2026-05-12
> **Triggered by:** Phase 133 walker swap exposed `.claude/*` and `.agents/*`
> leaking into the trace queue. The hot-fix (commit `34cb9ad2`) closed the
> immediate leak; this phase decides the broader policy.

---

## 1. The question

After the hot-fix, the catalog model in `DEFAULT_EXCLUDE_DIR_NAMES`
explicitly enumerates ~47 dirs to exclude (27 dot-dirs + 20 non-dot).
We considered three alternatives:

- **Model A (current)**: explicit catalog; everything else falls through
- **Model B**: deny all dot-dirs by default + allowlist exceptions
- **Model C**: respect `.gitignore` only; no catalog

The research below settled the question against Model B and C.

## 4. Three findings that change the answer

### Finding A — `.github/` is universal (20/23) and never gitignored

The single most-present dot-dir besides `.git/`. It carries CI workflows
(YAML), code-of-conduct, contribution guides, sometimes templates. **It
is architecturally relevant** — knowing the release/CI shape of a repo
informs how an agent should reason about deployment, gates, and review
flow. Model B would exclude it by default and require allowlisting.

Most repos don't gitignore `.github/` precisely because the workflow
files ARE the source of truth for CI.

### Finding B — Agent-instruction dirs are overwhelmingly prep-self-reference

The `.cursor/rules/` content across the sample was almost entirely:
- `.cursor/rules/prep.mdc` ("SourcePrep structural codebase intelligence")
- `.cursor/rules/codrag.mdc` (legacy CoDRAG version of the same)

Similarly for `.claude/`:
- `.claude/skills/prep.md` ("Get structural codebase context from Prep tools")
- `.claude/skills/codrag.md` (legacy)
- Project-specific skills like `.claude/skills/playwright-smoke/SKILL.md`,
  `.claude/skills/pipeline-testing/SKILL.md` (these ARE legitimate
  planning material)

For `.agents/`:
- SourcePrep's `.agents/AGENTS.md` is prep-auto-generated (carries
  `<!-- prep-opportunities-start -->` marker)
- OpenClaw's `.agents/maintainers.md`, `.agents/skills/.../SKILL.md`
  are genuine project workflow

**Implication:** including `.cursor/`, `.claude/`, `.agents/` blanket into
concept grounding is risky — most content would be prep's own output
fed back to the synthesizer, producing meta-recursive concepts like
"prep is a tool that gets structural context". A signal-based filter is
needed: skip files whose head contains "Auto-generated by Prep" /
"SourcePrep structural codebase intelligence" / "CoDRAG structural" /
`<!-- prep-managed-start -->`.

### Finding C — There exists a "real project dot-config" tier

Three dirs in the sample are dot-prefixed but contain legitimate
project metadata:
- `.devcontainer/` (2/23) — describes dev environment (Docker, VS Code
  extensions, post-create scripts)
- `.cargo/` (2/23) — Rust toolchain config (`config.toml`, vendor)
- `.mvn/` (3/23) — Maven wrapper config

None gitignored, none full of state. These ARE source-adjacent. Model
B would exclude them by default and require remembering to allowlist.

---

## 5. Why Model B fails

> "Skip all dot-dirs; allowlist exceptions"

The data shows three things that defeat it:

1. **`.github/` is universal architectural data.** Excluding it loses CI
   topology, gate descriptions, release flow. We'd need to allowlist it
   in EVERY project — exactly the kind of friction that catalogs avoid.
2. **Real project config dirs are dot-prefixed.** `.devcontainer/`,
   `.cargo/`, `.mvn/` are tracked by convention and contain genuine
   architectural info.
3. **The allowlist would grow as projects diversify.** Today: `.github`,
   `.devcontainer`, `.cargo`, `.mvn`. Tomorrow: `.deno/`, `.bun/`,
   `.pnpm-store/` (or not — these are caches), and unknown future
   tools. The maintenance burden is similar to Model A's catalog but
   the failure mode is worse (default lose, vs default leak).

Model B is intuitive when you think only about agent dirs. The data
shows the dot-dir universe is more heterogeneous than that.

---

## 6. Why Model C fails

> "Respect `.gitignore` only"

The data shows:
- `.claude/` is gitignored in **0/1** sample (SourcePrep itself doesn't
  gitignore the dir — only `.claude/worktrees/`).
- `.cursor/` is gitignored in **0/5** samples.
- `.agents/` is gitignored in **0/2** samples.
- `.pytest_cache`, `.mypy_cache`, `.ruff_cache` are mostly gitignored
  (1/1 each), but not always reliably (a fresh project may forget).

We cannot rely on the repo author's `.gitignore` to catch tool dirs.
Prep needs its own catalog as belt-and-suspenders.

## 7. Recommendation — refine Model A (catalog) along three axes

### 7.1 Add missing entries to `DEFAULT_EXCLUDE_DIR_NAMES`

Currently absent but observed in the sample (or known from convention):

| Dir | Reason |
|---|---|
| `.idea` | JetBrains IDE config — personal preferences |
| `.vscode` | Mixed — but default-exclude is safer; explicit opt-in via project config for teams who track it |
| `.junit.run` | IntelliJ JUnit run configs |
| `.opencode` | Future-proof agent-tool catch (already seen in 1 repo) |
| `.idea_modules` | JetBrains legacy |
| `.husky` | Git hooks framework — config not source |
| `.changeset` | Changesets versioning state |
| `.storybook` | Already in non-dot form; the dotted variant exists in some projects |

Plus pre-emptively (not in sample but well-known):
- `.bun/`, `.deno/`, `.pnpm-store/`, `.yarn/` (package-manager caches)
- `.fleet/`, `.zed/` (newer editors)

### 7.2 Explicitly DON'T exclude these (they fall through naturally)

| Dir | Reason |
|---|---|
| `.github/` | CI workflows — architectural; tracked by convention |
| `.devcontainer/` | Dev env description — architectural; tracked |
| `.cargo/` | Rust toolchain config — small, source-adjacent |
| `.mvn/` | Maven wrapper — source-adjacent |
| `.circleci/` | CI config |
| `.gitlab/` | CI config |
| `.azure/` | CI/deploy config |

Documenting these "intentionally NOT excluded" with a comment in
`repo_profile.py` makes the policy legible.

### 7.3 Add a `PREP_SELF_OUTPUT_FILE_MARKERS` filter for the concept synthesizer

The trace pipeline already excludes `**/CLAUDE.md`, `**/AGENTS.md`,
`**/.cursor/rules/*.mdc` (`DEFAULT_EXCLUDE_FILE_GLOBS`). The concept
synthesizer's `docs_grounding.py` walker has the OPPOSITE policy
(includes `.claude/`, `.cursor/`, `.agents/`). But "include the dir" ≠
"include every file in the dir" — we should filter prep-self-reference
files at the docs_grounding layer:

```python
# Markers that identify a file as prep-self-output. When grounding the
# concept synthesizer, skip these — including them would feed prep's
# own documentation back as planning material.
PREP_SELF_OUTPUT_MARKERS: tuple[str, ...] = (
    "Auto-generated by Prep",
    "Auto-generated by SourcePrep",
    "Auto-generated by RunPrep",
    "Auto-generated by CoDRAG",
    "SourcePrep structural codebase intelligence",
    "CoDRAG structural codebase intelligence",
    "RunPrep structural codebase intelligence",
    "<!-- prep-managed-start -->",
    "<!-- prep-opportunities-start -->",
    "Get structural codebase context from Prep tools",
    "Get structural codebase context from SourcePrep tools",
)
```

`docs_grounding.discover_planning_docs` reads each file's head to
extract excerpts already — we add an early skip when any of these
markers appears in the first ~500 chars.

This is the only way to get useful content out of agent-instruction
dirs in a prep dogfooding context. Without it, the synthesizer's
grounding is dominated by self-reference.

## 9. Open question (for the user)

**`.vscode/` is the borderline case** — 2 of 4 sample repos gitignore
it, 2 track it. Teams that share `launch.json` configs across a project
get value from tracking it; teams that don't get noise. The default
(exclude) is right for the median case, but worth surfacing as
"intentionally excluded; opt-in via project config if your team
shares VS Code settings."
