## `prep_observe` vs Claude Code auto-memory — honest assessment

**Empirical baseline:** `prep_observe(action=get)` returned zero observations across all queries in this project. The local Claude Code auto-memory dir at `~/.claude/projects/<hash>/memory/` has 32 active markdown files. Across a month of dogfooding, agents have voted with their tool calls.

**For a solo Claude Code user, today, `prep_observe` is largely redundant** with auto-memory. Both are persistent, both survive sessions, both are categorized.

But three properties of `prep_observe` (verified in `src/prep/services/observation_store.py`) are structural capabilities auto-memory cannot match:

1. **Cross-agent portability.** Auto-memory is Claude-only. A Cursor / Windsurf / Copilot / Continue user opening the same repo gets none of those 32 files. `prep_observe` is daemon-served — any MCP-aware agent reads the same store. If SourcePrep's positioning is "shared brain across agents," this is the only mechanism that delivers that.
2. **File-anchored staleness.** Auto-memory has no link to code. Write "auth lives in `api/auth.py`," rename the file, and the memory silently rots — every session reads it as truth. `ObservationStore.mark_stale_batch` flags observations when their anchor file changes. Real product value, but only if observations are actually anchored at write time.
3. **Time-travel (`as_of`).** `as_of` returns observations valid at a Unix-epoch point in time. Useful for retroactive debugging ("what did we know on 2026-04-15 when this bug was filed?"). Auto-memory is always "current."

### Strategic implication

These three properties only matter if observations are **project-shared and travel with the repo**. Today they don't — the store is per-daemon-instance and empty. My take:

> Declare an explicit split: `prep_observe` is for **project-shared facts that should travel with the codebase** (commit to `.sourceprep/observations.db` or similar). Claude auto-memory remains for **personal preferences and per-user feedback**. Without this distinction, agents will keep defaulting to auto-memory and `prep_observe` stays empty.

If we don't make that split, the right move is to drop `prep_observe` and lean on the host agent's memory primitives.

The current state — feature shipped, no canonical use case, empty store — is the worst of both worlds.

## Initial research direction

The atlas-generation pipeline is **one codebase region** producing four user-visible defects (FIX-16-1, -3, -4, brand drift). Fix it as one focused pass, not four scattered tickets.

### Sequencing

1. **FIX-16-1 (firehose default)** — highest leverage. Every `prep()` call in every session pays the tax. Direct conflict with "refresh during long tasks" guidance the skill itself ships.
2. **FIX-16-3 (`#N` duplicate suffix)** — clustering bug, probably one post-process pass on synthesized module names.
3. **FIX-16-4 (consulting voice)** — prompt-level fix in the module-summary synthesis prompt + a lint pass that re-prompts on banned phrases.
4. **Brand drift** — one-line atlas-identity fix to canonicalize "SourcePrep" / strip "CoDRAG" mentions from generated artifacts.

### FIX-16-1 — corrected diagnosis after code investigation

Initial assumption was that the firehose came from the atlas section. **That was wrong.** Code-walk shows:

- `src/prep/mcp/server.py:1051-1140` — atlas inclusion is already conditional. ISSUE-6 + Phase 73.4 hash-match logic skips the atlas when the rules file (CLAUDE.md/AGENTS.md) already carries it.
- `src/prep/mcp/server.py:146-164` — Claude budget is 50 K, +50 % first-call orientation boost (75 K). That's the *budget*, not the *output*.

The actual firehose source is **`_format_module_tiers`** in `src/prep/api/routers/projects/search.py:433-512`:

1. It iterates **every** "significant" module (`file_count >= module_min_files_significant`) and emits each with a multi-sentence consulting-deck summary plus deps line.
2. There is **no per-module truncation** and **no max-modules cap**.
3. In `_assemble_ambient_context` (lines 588-593), `mod_text` is appended to `parts` *unconditionally* before any budget check — only the remaining budget after the module dump flows to hub files / neighbors.

`ContextTier` (Tier 1) sets `module_min_files_significant=5` and `module_show_small=True, module_show_tiny=True`. On a 1 897-file repo that promotes ~50 modules to "significant" — exactly what the live `prep()` output shows.

So the bug is structural, not a budget knob:

- Lowering `_DEFAULT_BUDGET` would only starve hub files; module text remains uncapped.
- The atlas-skip mechanism is correct and already shipping.

### FIX-16-1 — concrete proposal

Two surgical changes, both in the assembler layer:

1. **Cap the module list** in `_format_module_tiers`. Add a `max_modules` param (sourced from `ContextTier`, e.g. Tier 1 = 12, Tier 2 = 8, Tier 2.5 = 6). Modules beyond the cap fold into the "smaller modules" footnote.
2. **Truncate each module summary** to its first sentence by default (the synthesizer already produces multi-sentence summaries; the rest is consulting-deck filler — which also closes FIX-16-4 partially). Add a `verbose=True` param to `_format_module_tiers` for callers who want the full text.

Optional safety net (Option B): add `module_budget_pct` to `ContextTier` (e.g. 0.25 of total budget) and clip `mod_text` against it before appending in `_assemble_ambient_context`. This guarantees the module list can never starve hub/neighbor budgets even if a future synthesizer regresses.

**Risks:**

- Capping modules reveals ranking quality. Today the list is sorted by `file_count` (or role-affinity when `role=` is set). With a 12-module cap, file-count ordering might omit a small-but-important module the agent needed. Mitigation: respect the existing role re-rank, and surface omitted-module count in the footnote so the agent knows to ask for `verbose=True`.
- First-sentence truncation depends on summaries actually starting with the most informative sentence. Some current summaries don't (FIX-16-4 territory). Mitigation: ship the cap first, fix the prompt second.

**No change** to `_CLIENT_BUDGETS` or `_get_context_budget()` proposed in this pass — those are correct as designed once the module list is bounded.
