# 18 — Follow-up Dogfooding (2026-05-09)

Three product-feedback datapoints surfaced naturally while debugging a user-reported
watcher / Auto-Manual-toggle bug. Logging here so they don't get lost in the
implementation work.

## 1. `prep_search` intent classifier over-triggers `locate` / `trace` on descriptive prose

**What happened:** Multi-word natural-language queries got auto-classified as
`trace` or `locate`, both of which expect a literal node name and threw
`NODE_NOT_FOUND` instead of falling back to semantic search.

| Query | Auto-detected intent | Result |
|---|---|---|
| `"file watcher auto incremental sync trigger"` | `trace` | `NODE_NOT_FOUND: Node not found: file watcher auto incremental sync trigger` |
| `"rebuild endpoint discover stale new files"` | `trace` | `NODE_NOT_FOUND` (same) |
| `"where is the file watcher debounce"` | `locate` (symbol mode) | `No symbols found matching: the file watcher debounce` |
| Same first query with explicit `intent="explain"` | `explain` | Returned `AutoRebuildWatcher._on_coverage_check` and `file:src/prep/core/watcher.py` immediately |

**Pattern:** the classifier appears to weight the keywords (`where`, `find`,
`trigger`) over query length / shape. A 7-token descriptive phrase is almost
never a literal symbol name — it should fall back to `explain` rather than
fail closed.

**Suggested heuristic:**

- If query has ≥4 tokens AND no exact symbol-character match in first attempt,
  re-run as `explain` automatically rather than returning `NODE_NOT_FOUND`.
- For `locate`: require either a single bare token, an `@path:line` shape, or
  a clear "where is X" / "find X" pattern where X is a single identifier-like
  token. Multi-word descriptions should not trigger symbol mode.
- This compounds the FIX-2026-05-08 datapoint (`prep_search "where is the prep
  no-arg ambient context budget…"` returned no symbols) — same class of bug.

This is also relevant to Phase 124's intent classifier work — confirms the
"NODE_NOT_FOUND should never be a user-visible response from prep_search" thesis.

## 2. UI optimistic-default lie: dashboard toggle painted "Auto" while watcher was muzzled

**What the user saw:** FAST SYNC Auto/Manual pill displayed "Auto" with a green
"Watching" badge.

**What was actually true:**
- per-project `auto_config = null` (toggle had never been clicked)
- global `pipeline_config.fast_sync.auto = false`
- watcher gates (both `_on_coverage_check` and the debounce-fire callback)
  read the global, returned False, refused to fire builds
- the watcher was capturing events but the trigger pipeline was muzzled

**Root cause:** `useTraceSystem.ts` had three separate `?? true` defaults that
painted `fastSync: true` whenever the per-project key was missing. The toggle
displayed the optimistic local-state default, not what the daemon actually
believed.

**Dogfooding lesson for product:** *Visual indicators must reflect daemon
state, never optimistic local defaults.* When the truth is unknown, default
to the more cautious display (Manual) — same defensive principle the gate
already uses.

A bonus contributor: the gate and the UI defaults disagreed on what "missing"
means. Gate: missing = False (manual). UI: missing = True (auto). The two
should be derived from a single source of truth — likely a shared schema /
default constant. Worth adding a "default-value drift" check.

**Fixed in this session:** `useTraceSystem.ts` defaults flipped from `?? true`
to `?? false` in all three sites.

## 3. Backend gate inconsistency between fast_sync (global) and deep/finalize (per-project)

**Discovered while reading the code:** the orchestrator was just refactored
(uncommitted in the working tree at session start) so `_is_deep_enrichment_auto`
and `_is_finalize_auto` only consult per-project `auto_config`, with this
explicit comment:

> *"The legacy global fallback was the regression that caused projects with
> their UI on Manual to auto-chain whenever a stale global
> `pipeline_config.deep_enrichment.mode` was still set to auto."*

But `fast_sync`'s gates were not migrated:

- `src/prep/core/watcher.py:_on_coverage_check` — read global `pipeline_config.fast_sync.auto`
- `src/prep/api/routers/projects/watch.py:trigger_build` — same

**Dogfooding lesson:** *When migrating a config schema (per-project ⇄ global),
ALL gates that consult that key must move together*, otherwise the system
operates with two contradictory authorities. This is exactly the bug class
Phase 82 surfaced for atlas brand drift — single concern, multiple readers,
partial migration.

A code-level guard would be a `tests/test_auto_config_gates.py` that
parametrically asserts every `_is_*_auto` reader uses the same lookup path
(per-project first, no global fallback). Worth adding to the immune system —
this fits the "constraint concept → antibody" pattern.

**Fixed in this session:** added `PipelineOrchestrator._is_fast_sync_auto`
mirroring the deep/finalize pattern; both watcher gates now call it.

## 4. State-sync gap: external rebuild didn't drop watcher's `pending_paths` / `stale_since`

**Symptom (user-reported):** "if I manually click rebuild it rebuilds but
fails to include the stale/new files in the rebuild."

**What was happening:** the watcher's `pending_paths` and `stale_since` are
written by its own debounce path (`_queue_path`). When the user clicks
Rebuild externally (`POST /pipeline/rebuild` → `run_all(force_from_start=True)`),
the rebuild clears `_changed_paths` (Phase 118 U16) and the Rust walker does
a full disk scan — but the *watcher's* `pending_paths` set survives the
rebuild. Result: dashboard keeps showing "stale" and the user concludes the
rebuild didn't process the changes.

**Dogfooding lesson:** *State that's read from one subsystem and written by
another must have a contractual sync point.* The rebuild was the consumer
of the watcher's queued changes, but no code path acknowledged that
consumption. This is also a coupling smell worth a concept anchor.

**Fixed in this session:** added `AutoRebuildWatcher.clear_pending_state()`
and called it from the orchestrator's `force_from_start` branch right after
the U16 cleanup. Pipeline file logger now records `watcher_pending_consumed`
when this fires non-trivially.

## Closing note (Phase 133 follow-up, 2026-05-10)

The "filter divergence is real" finding documented under §3 above
(2026-05-09 dogfooding session) was the trigger for **Phase 133 —
Rust Walker/Hasher Cutover**. That phase removed the root cause:
`compute_trace_coverage` and `_compute_file_hashes` now walk via
`prep_engine.walk_repo` (the same primitive the structural rebuild
uses), and hashing moved to `prep_engine.hash_content` (BLAKE3-128)
with self-healing manifest migration via the new `hash_algo` field.

The 6-surface divergence map from this dogfooding doc is now closed
by construction. See `docs/Phase133_RustWalkerHasherCutover/README.md`
for the full spec and `IMPLEMENTATION_PLAN.md` for the change manifest.

Phase 133 also did adjacent brand cleanup: dropped legacy
`**/.codrag/**` and `**/codrag_data/**` exclude patterns from Python
defaults and the test assertions that pinned them, since the rename
to SourcePrep is settled.

The U19 logging the spec calls out as a *symptom mitigation* can be
removed in a future phase (the divergence it logs no longer occurs);
left in place pending the full release cycle that proves Task 7's
runtime assertion stays green in production.
