# 20 — Follow-up Dogfooding (2026-05-13)

Two `prep`-side findings surfaced during the Phase 132 docs audit
(scrutiny passes on the panel-registry, MCP page, and model-advisor
guide). Both are out of scope for Phase 132 itself — recording here
so a future MCP-cluster session can pick them up cleanly.

## 1. Sparse `prep` no-arg atlas (1 of 10 modules returned)

**Observed:** calling `prep` with no arguments returned a near-empty
ambient context — exactly one module entry ("Roadmap & Sprint
Planning Orchestrator") with `0 concepts (0 active, 0 seed) + 1
module rationale (0 active, 1 seed)`. The static atlas snapshot
embedded in `CLAUDE.md` frontmatter at the same moment listed
**all ten** subsystems with rich descriptions, hub files, cross-
cutting concerns, and call chains.

**Reproduction:** 2026-05-10 and 2026-05-12 sessions, daemon up,
project `f1636374-abc6-410d-99ee-822120379e79`, no project_id
override, fresh `prep` call after `/mcp` reconnect. Same result both
times.

**Why it matters:** the dogfooding rule says "call `prep` at the
start of every task." If the no-arg response is structurally thinner
than the static CLAUDE.md atlas dump it replaces, the rule is
actively misleading — agents who follow it lose context relative
to agents who just read CLAUDE.md.

**Hypotheses to test:**

- Module-filter / role-projection over-trim. The MCP server's
  ambient context budget logic (`src/prep/mcp/server.py:123-138`
  `_CLIENT_BUDGETS`) projects per-client. The Claude Code budget
  may be aggressively filtering modules below a relevance threshold
  that's miscalibrated when no query is supplied — relevance to
  "no query" is undefined, so any positive threshold ejects most
  modules.
- Atlas-source divergence. The static CLAUDE.md atlas reads from
  the on-disk `atlas.json` artifact. The live `prep` call may read
  from a different in-memory source (e.g. the structural cache that
  hasn't been re-hydrated since the last full Finalize stage).
  Compare `core/atlas/loader.py` paths for `prep` vs the CLAUDE.md
  regeneration codepath.
- Project-id misrouting. The bare `prep` (no `project_id` arg)
  may be falling back to a default-project or the most-recently-
  built project, which could be a different project than the one
  whose atlas CLAUDE.md was generated from.

**Recommended follow-up:**

- [ ] **P82-F5: instrument the no-arg `prep` codepath.** Log the
  resolved project_id, the loader source (cache vs disk), and the
  pre-projection module count vs the post-projection count.
  Compare against the count in the on-disk `atlas.json`.
- [ ] **P82-F6: tighten or remove the relevance threshold for
  no-query ambient context.** "No query" should default to showing
  the full structural overview, not an aggressively trimmed slice.

Anchors: `src/prep/mcp/server.py` (ambient context handler),
`src/prep/core/atlas/loader.py`, `CLAUDE.md` (auto-managed atlas
section regenerated via `core/rules_generator.py`).

## 2. LLM module-summary brand drift (CoDRAG strings survive scrub)

**Observed:** the Phase 130 Issue 13 fix landed two scrubbers — the
structured-field IDENTITY brand-drift fix
(`tests/test_atlas_identity_brand.py`) and the `git_evidence`
ghost-directory filter for `Active zones`
(`tests/core/test_git_evidence.py`). After those landed, IDENTITY
reads `SourcePrep` and `Active zones` no longer mentions `codrag/`.

But CLAUDE.md atlas frontmatter line 335 (the "Dashboard State &
Component Refactoring Tracker" module summary) still ended:
`"...across the CoDRAG dashboard"`. The string is LLM-generated
free text from a per-module summarizer, not a structured field —
so the brand-drift fix didn't cover it.

**Why it matters:** the bigger Phase 13 / Phase 130 scrub-story
was "the live atlas no longer leaks the legacy codename." Today
it does, in user-visible LLM prose. Anyone reading the atlas in
CLAUDE.md (or in the static MCP resource feed) still sees CoDRAG.

**Fix shape — two reasonable approaches:**

- **Re-run module-summary synthesis after registry rename.** When
  a project's display name changes (registry update), invalidate
  the cached `cluster.MODULE_SYNTHESIS` outputs and regenerate.
  Heavy-handed but correct.
- **Post-process summary text at atlas-render time.** Hold a
  brand-replacement table (`CoDRAG → SourcePrep`, `prep_data →
  ~/.local/share/sourceprep`, etc.) and substitute on read.
  Cheaper, but accumulates a maintenance burden over time as
  more legacy names appear.

The first approach scales better as the project picks up more
codename history. The second is a quick mitigation if the LLM
re-run is expensive.

**Recommended follow-up:**

- [ ] **P82-F7: invalidate-and-regen module summaries on project
  rename.** Hook into the registry rename path; mark
  `cluster_summaries.json` (or equivalent) stale; let the next
  Finalize pass refresh.
- [ ] **P82-F8: optional safety net — atlas-render brand
  substitutor.** A tiny replacement table applied on read of any
  free-text atlas field. Defense-in-depth so a single missed
  invalidation doesn't ship a poisoned summary.

Anchors: `src/prep/core/atlas/generator.py` (summary rendering),
`src/prep/core/cluster.py` (`MODULE_SYNTHESIS_PROMPT`,
`MODULE_SYNTHESIS_SYSTEM`), `prep_observe` bug id `ff75c58924d7`
(saved 2026-05-10).
