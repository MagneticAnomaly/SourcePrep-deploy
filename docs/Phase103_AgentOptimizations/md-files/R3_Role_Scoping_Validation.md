# R3 — Knowledge-Honing Validation (Keep-or-Refine Decision)

**Read `00_CLARIFICATION.md` first.** This sub-phase tests **knowledge-honing** (graph-based sub-atlas filtering), not persona prompting. The two are mechanistically distinct; this investigation is about the former.

**Goal:** Empirically determine whether role-weighted sub-atlas context outperforms uniform-atlas context on real code tasks.
**Time budget:** 2 weeks
**Decision at end:** keep, refine weighting, or revise — we are not looking to kill the feature, we are looking to measure how well the existing sub-atlas engine performs and where it needs tuning.

## Core question

CoDRAG already computes role vectors and role-weighted sub-atlases (Phase 67 + Phase 88). The UI and engine exist. What we have never measured is: **does serving a role-weighted sub-atlas to an agent produce measurably better task output than serving the full atlas?**

This is the central empirical question of Phase 103. Our architecture assumes knowledge-honing helps. Every feature we've proposed — Paperclip per-role context, Claude Code subagent carriers, OpenClaw sub-atlas configs — assumes it. **The mechanism works under the hood, but its impact on agent performance is the untested leg.**

Importantly: this is **not** the same question as "does persona prompting help?" (answered negatively by existing research). It is its own empirical question about knowledge selection via a graph — a question the literature largely does not address.

## Hypothesis

**H1 (our core thesis):** A role-weighted sub-atlas improves agent output quality over a uniform atlas because it (a) reduces context-rot from irrelevant content and (b) prioritizes files, concepts, and antibodies the agent most needs for the task — all without changing the agent's instructions.

**H2 (the uncomfortable alternative):** At agent-typical context sizes (2–8K), the model's own attention mechanism already filters irrelevant content effectively. Our graph-based pre-filtering is redundant work.

**H3 (the nuanced middle):** Sub-atlas weighting helps at larger budgets (where rot bites) but offers little at small ones (where context is already constrained by size). The value scales with budget — meaning our sweet spot is likely in the 4–16K range.

**H4 (the calibration possibility):** Knowledge-honing helps, but our current role-vector weights are suboptimal. A measurable but modest improvement over baseline indicates the mechanism works but needs tuning, not that the thesis fails.

Note: **persona prompting is expected to be a non-factor or slightly negative**, consistent with the literature. R3 includes it as a control axis — not to test our thesis but to confirm that persona-prompting literature results reproduce on our tasks, so we can cleanly attribute any observed improvement to knowledge-honing rather than persona framing.

## Literature check

**On persona prompting (the axis we're controlling for, not testing):**
- **Expert Personas Improve Alignment but Damage Accuracy (arxiv 2603.18507)** — persona prompts can hurt accuracy.
- **PersonaGym (ACL 2025)** — effectiveness is task-and-model-dependent.
- These inform our control axis only.

**On knowledge-graph-based scoping (the axis we're actually testing):**
- **Codebase-Memory (arxiv 2603.27277)** — tree-sitter + knowledge graph via MCP; 83% answer quality at 10× fewer tokens vs. file-exploration. Measures graph-over-file retrieval, not role-weighted sub-atlas specifically.
- **Agent-MCP (github.com/rinadelph/Agent-MCP)** — coordinated specialist agents via MCP; assumes but does not measure that role-scoped knowledge helps.
- **Anthropic context engineering** — endorses "just-in-time retrieval" generally; no specific finding on role-weighted pre-filtering.
- **Augment Code's "Deep Context Threading"** — markets a similar idea (map of what connects to what) but publishes no empirical comparison.

The key point: **no published study directly measures the impact of role-weighted sub-atlas selection on code-agent task performance.** This is novel empirical territory, which is exactly why R3 matters. We are not re-running persona-prompting research; we are running the first test of our specific mechanism.

**Critical mechanistic distinction (repeated for emphasis):**
- Persona prompting changes the agent's *instructions* ("you are a paranoid security engineer"). Empirically mixed.
- Knowledge-honing changes the agent's *corpus* (a sub-atlas pre-filtered to security-relevant files + concepts). Not separately tested in the literature.

These are different interventions at different layers. Our experiment must separate them cleanly.

## Experiment design

R3's contribution is a clean factorial test that separates knowledge-honing from persona prompting.

**Factors (2×2):**
- **Knowledge axis (the one we care about):** uniform atlas ↔ role-weighted sub-atlas (generated by our existing sub-atlas engine)
- **Persona axis (control):** no persona prompt ↔ persona prompt ("You are a security engineer reviewing this code...")

**Four cells:**
| | Uniform atlas | Role-weighted sub-atlas |
|---|---|---|
| No persona prompt | A (baseline) | **B (CoDRAG's pure thesis — knowledge only)** |
| Persona prompt | C (persona-only — the AGENTS.md convention) | D (both — Paperclip's current default) |

**The primary comparison is B vs A.** If B meaningfully beats A without any persona instruction added, knowledge-honing alone carries the win. That's our core thesis validated.

Secondary comparisons:
- C vs A — does persona prompting alone do anything? Expected: little or negative, consistent with literature.
- D vs B — does stacking persona on top of knowledge-honing add or subtract? If D ≤ B, recommend removing persona prose from Paperclip SOUL.md.
- B vs D — is our current Paperclip default (D) actually better than the pure knowledge-only condition (B)? If not, simplify Paperclip.

**Tasks:** 30 tasks on CoDRAG's own repo, deliberately chosen to span roles — 10 security-flavored, 10 frontend-flavored, 10 backend-flavored. Each task has an objective rubric (correct file identified, correct fix applied, correct rationale given).

**Run:** each task × each cell × 3 trials. 360 runs total. Sonnet 4.6.

**Measure:**
- Task success rate per cell.
- Output quality (rubric score 1–5).
- Token cost per cell.
- Hallucination rate (references to nonexistent files, claims about code that isn't there).

## Outcomes and decisions

Four plausible patterns, each with a distinct decision. Notably, no outcome calls for killing knowledge-honing outright — the worst credible outcome is "our weighting needs tuning," which is a calibration problem, not a thesis failure.

### Pattern 1 — Knowledge-honing wins, persona is neutral (B ≈ D > A ≈ C)
**Interpretation:** The sub-atlas engine is doing its job. Persona prompting contributes little.
**Decision:** Ship knowledge-honing as the primary product surface. Strip persona prose from Paperclip SOUL.md and all emission carriers. Our MCP responses deliver scoped knowledge; the host decides whether to wrap persona around it (default: don't).
**Simplification:** Remove the persona-generation paths — they're not earning their complexity.

### Pattern 2 — Both axes contribute independently (D > B > C > A or D > C > B > A)
**Interpretation:** Knowledge-honing and persona prompting both add value; they stack.
**Decision:** Keep both. Paperclip's current SOUL.md+KNOWLEDGE.md design is validated. Knowledge-honing becomes the default for MCP responses; persona prose stays as an opt-in layer.
**Simplification:** None — current architecture is validated.

### Pattern 3 — Persona damages accuracy (B > D, A > C)
**Interpretation:** Knowledge-honing is the value; persona prompting actively hurts.
**Decision:** Strip persona prompts from all default outputs. Document the finding. Paperclip SOUL.md becomes a thin role-label + tool allowlist; the content is the role-weighted sub-atlas.
**Simplification:** Aggressive but earned by data.

### Pattern 4 — Neither axis matters at our budgets (A ≈ B ≈ C ≈ D)
**Interpretation:** At 2–8K context, the model's own attention handles filtering; our sub-atlas weighting provides no measurable lift, and persona prompting doesn't either. This is the "do nothing helps" outcome.
**Decision:** **Do not kill the feature.** This is a calibration signal, not a thesis falsification. Two responses are appropriate:
1. **Tuning pass on role-vector weights.** If our domain/layer/hub weights are miscalibrated, the sub-atlas may not meaningfully differ from uniform. Re-run R3 after tuning.
2. **Test at larger budgets** (16K, 32K). Our thesis may only show value where context rot bites hardest.

Only after targeted tuning + budget expansion still shows no lift should we reconsider the thesis. Even then, the sub-atlas remains useful for UI filtering and cold-start orientation; the question becomes whether to expose it as a primary MCP surface.

### Pattern 5 — The expected finding: Pattern 1 or 2 with modest effect size
**Interpretation:** Knowledge-honing produces a 5–15% improvement on task success and/or a 2–5× reduction in tokens-to-success. This is a good outcome and matches the intuition behind our architecture. Not a miracle; a solid, publishable effect.

This pattern is what we should plan for and what the product story should be calibrated against. Anything better is upside.

## Simplicity audit

Before we run the experiment, consider whether there's a cheaper way to answer the question.

- Can we introspect an agent's attention patterns to tell whether it uses in-scope vs. out-of-scope content? Not reliably, not for closed models.
- Can we use a smaller eval (5 tasks instead of 30)? Probably — if the effect size is large, 5 tasks × 4 cells × 3 trials (60 runs) is enough to see it. Start there.
- Can we test just two cells (A vs. D) instead of all four? Loses the ability to distinguish scope-vs-persona, which is the whole point. Don't skip.

**Refined plan:**
- Phase 1 (2 days): 5-task pilot across all 4 cells, 3 trials each = 60 runs. Look for effect size.
- Phase 2 (if pilot shows signal): expand to 30 tasks for confident statistics. 1.5 weeks.
- Phase 3 (if pilot shows no signal): stop. Role projection fails Pattern 4. Write up the falsification. Simplify the product dramatically.

## Consequences of each outcome

| Outcome | Product impact |
|---|---|
| Pattern 1 | Knowledge-honing validated solo. Cut persona generation from defaults. Emit knowledge-only `codrag()` responses. Phase 88 SOUL.md becomes a thin wrapper over KNOWLEDGE.md. |
| Pattern 2 | Both axes validated. Ship existing design. Paperclip's default is already correct. |
| Pattern 3 | Strip persona actively. Document the counter-evidence. Ship knowledge-only as default; persona as opt-in with warning. |
| Pattern 4 | Calibrate: re-weight role vectors; re-run at larger budgets; if still no lift, demote from primary surface but keep as internal UI-filter. Thesis not killed — demoted until re-validated. |
| Pattern 5 | Expected: modest lift. Ship, measure improvements over time as sub-atlas engine refines. Publish numbers. |

## Why this is THE most important sub-phase

Every architecture we've designed — Phase 88 role generation, Phase 103 subagent emission, the "single source of truth" vision in 04, the Paperclip integration — rests on knowledge-honing being valuable. The mechanism is built; the empirical validation isn't done.

R3 tells us:
- **Whether our already-built sub-atlas engine produces measurable agent-quality gains.**
- **How much lift it produces**, so we can calibrate expectations and marketing claims.
- **Whether persona prompting should be stripped, kept as opt-in, or left as default.**
- **Whether our current role-vector weights are well-calibrated** or need tuning.

The research is not "should we build this?" It's "how well does the thing we already built perform, and what does it need?" That's a stronger, more focused question than the earlier draft implied.

**Run R3 early. Use its data to tune Paperclip's current default and the forthcoming universal API (R4). Do not defer.**
