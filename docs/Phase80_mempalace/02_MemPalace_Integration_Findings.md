# Phase 80: MemPalace Integration — Findings & Recommendations

> Date: 2026-04-07
> Status: Research Complete
> Goal: Identify where MemPalace patterns can make Prep a better product

## Executive Summary

After deep examination of both codebases, we identified **three high-value integration opportunities** and **two patterns to skip**. The focus is on making Prep better at what it already does — not bolting on new features.

---

## Track A: AAAK-style Compression for Swarm Communication

### What MemPalace Does
The `Dialect` class in `dialect.py` converts natural language into a plain-text symbolic notation achieving ~30x compression. Entities become 3-letter codes (`ALC=Alice`), emotions become 2-4 char codes, and structural flags (`ORIGIN`, `CORE`, `DECISION`, `PIVOT`, `TECHNICAL`) tag content semantics. Format:

```
wing|room|date|source
0:ENTITY+LIST|topic_keywords|"key_sentence"|emotion_codes|FLAGS
```

Key design choice: **no decoder needed**. Any LLM can read it because compression comes from structural abbreviation, not encoding.

### What Prep Has Today
- `core/lod_extractor.py`: 6-level lossy compression for *code* context (LOD 0-5, up to 20:1 ratio)
- `core/compressor.py`: Abstract `ContextCompressor` base class with `NoopCompressor` as the only implementation — a clear extension point waiting to be filled
- `core/swarm_orchestrator.py`: Three-phase parallel LLM analysis where `WorkItem` objects carry `summary` + `full_context` between coordinator and workers
- Inter-stage data: JSONL files between pipeline stages, no compression applied

### Assessment: ADAPT THE PATTERN, NOT THE CODE

**Don't port AAAK directly.** AAAK is designed for personal memories (people, emotions, life events). Prep deals in code structures (modules, dependencies, symbols). The *pattern* to adapt is:

1. **Symbolic shorthand for structural entities** — Instead of repeating full file paths and module names in swarm worker assignments, use a registry of 3-4 char codes: `SWO=swarm_orchestrator.py`, `OBS=observation_store.py`. The coordinator plan already decomposes work into `WorkerAssignment` objects; the summary field could use these codes.

2. **Structural flags on context chunks** — Tag context blocks with flags like `HUB` (high fan-out), `ENTRY` (entry point), `STALE` (staleness-flagged), `CYCLE` (part of import cycle). This metadata is already available from the trace graph but isn't surfaced in compressed context.

3. **Fill the `ContextCompressor` extension point** — Implement a `StructuralCompressor` subclass that: (a) builds a symbol registry from the trace graph, (b) replaces FQNs with short codes, (c) prepends a legend, (d) strips redundant structural scaffolding. This slots directly into `compressor.py`'s existing interface.

### Where to Implement
| What | Where | Effort |
|------|-------|--------|
| Symbol registry for short codes | New: `core/compression/symbol_registry.py` | Small |
| Structural flag tags on chunks | `mcp/server.py:_format_context_response()` | Small |
| `StructuralCompressor` implementation | `core/compressor.py` (new subclass) | Medium |
| Swarm assignment compression | `core/swarm_orchestrator.py` coordinator prompt | Small |

### Expected Impact
- **Token reduction in swarm**: 30-50% on coordinator↔worker payloads (paths and FQNs are highly repetitive)
- **Better LLM comprehension**: Structural flags give models explicit signals about code importance
- **No breaking changes**: `ContextCompressor` interface is already abstract; `NoopCompressor` remains default

### Risks
- Short codes must be deterministic and collision-free within a project
- Legend must fit within context budget (mitigated: registries are small, ~20-50 entries for most projects)
- Must validate that target models (especially Haiku) reliably parse the shorthand 

### Verdict: **DO THIS** — Medium priority, high ROI

## Track B: Layered Memory Stack

### What MemPalace Does
A 4-layer `MemoryStack`:

| Layer | Name | Size | Loading |
|-------|------|------|---------|
| L0 | Identity | ~100 tokens | Always loaded |
| L1 | Essential Story | ~500-800 tokens | Always loaded |
| L2 | On-Demand | ~200-500/call | When topic arises |
| L3 | Deep Search | Unlimited | Explicit queries |

Wake-up cost: ~600-900 tokens. The rest of context is free for the task.

### What Prep Has Today
- **Atlas** (generated by `core/atlas/`) = roughly L0+L1: project identity, stack summary, workspace map, hub files. Always included in `prep` ambient response.
- **`prep_search`** = L3: full semantic search with trace expansion.
- **No explicit L2**: There's no "give me just the observations and concepts relevant to *this specific module*" without running a full search.
- **Observation Store** has `visibility` (shared/private/internal) and `created_by` fields — the infrastructure for agent-scoped memory exists but isn't layered.

### Assessment: FORMALIZE THE LAYERING WE ALREADY HAVE

Prep's context assembly in `mcp/server.py` already does implicit layering:
1. Atlas (always included if fresh) — this IS L0+L1
2. Search results with trace expansion — this IS L3
3. Concept augmentation (top 2-3 concepts appended) — this is a weak L2

**The gap is an explicit L2: module-scoped retrieval.** When an agent is working in `src/prep/services/`, they should be able to get observations, concepts, and recent changes scoped to that directory without a semantic search query. This is metadata-filtered recall, not embedding similarity.

### Where to Implement
| What | Where | Effort |
|------|-------|--------|
| Module-scoped observation retrieval | `observation_store.py`: add `get_for_directory(project_id, dir_path)` | Small |
| Module-scoped concept retrieval | `concept_store.py`: add `get_for_directory(project_id, dir_path)` | Small |
| L2 layer in context assembly | `mcp/server.py:_format_context_response()` — detect working directory from query context, include scoped observations/concepts | Medium |
| Working directory hint in MCP tools | `mcp_tools.py`: add optional `working_dir` parameter to `prep` and `prep_search` | Small |

### What NOT to Port: Agent Diaries
MemPalace's "diary" pattern (each agent gets its own wing with diary entries in AAAK format) is **not needed**. Prep's `observation_store` already has `created_by` and `visibility` fields. The `prep_observe` MCP tool already supports per-agent save/get. Adding a separate "diary" system would create dual sources of truth — exactly the risk called out in the research strategy.

Instead: **leverage existing `visibility=private` + `created_by` filtering** to give agents the equivalent of private diaries. If an agent saves with `visibility=private, created_by="architect"`, only that agent's queries should return those observations. Check that `get_for_query()` actually filters on these fields (current implementation may not).

### Expected Impact
- **Faster module-level orientation**: Agents get relevant observations/concepts without formulating a search query
- **Better context efficiency**: L2 retrieval is cheaper than L3 (metadata filter vs. embedding search)
- **Agent continuity**: Private observations already give cross-session memory per agent role

### Risks
- Working directory detection heuristic may be unreliable (mitigated: explicit `working_dir` parameter)
- L2 results may overlap with L3, wasting context budget (mitigated: dedup before assembly)

### Verdict: **DO THIS** — High priority, the gap is real and the fix is small

## Track C: Temporal Validity on Knowledge

### What MemPalace Does
SQLite `triples` table with `valid_from TEXT, valid_to TEXT`:
```sql
WHERE (valid_from IS NULL OR valid_from <= ?)
  AND (valid_to IS NULL OR valid_to >= ?)
```
Old facts are never deleted — they get an end date via `invalidate()`. Enables point-in-time queries: "what was true about entity X on date Y?"

### What Prep Has Today
- **Concepts**: `stale INTEGER DEFAULT 0, stale_reason TEXT` — binary flag, no history
- **Observations**: Same pattern — `stale INTEGER DEFAULT 0, stale_reason TEXT`
- **Staleness flow**: `watcher.py` detects file changes → `scope_orchestrator.py` → `mark_stale_batch()` sets `stale=1` on observations/concepts linked to changed files
- **Pruning**: `concept_store.prune_stale()` deletes stale concepts older than threshold — **destructive, no history preserved**

### Assessment: PARTIAL ADOPTION — ADD TEMPORAL COLUMNS, KEEP CURRENT FLOW

Full temporal graph (MemPalace-style triples) is overkill for Prep. Prep tracks *concepts about code*, not *relationships between entities*. But the `valid_from`/`valid_to` pattern solves a real problem:

**Today's failure mode**: A concept gets marked stale, then pruned. Three months later, someone asks "why did we choose this architecture?" The answer was in a concept that got deleted. With temporal validity, the concept would still exist with `valid_to` set — queryable with `as_of` semantics.

### Where to Implement
| What | Where | Effort |
|------|-------|--------|
| Add `valid_from`/`valid_to` columns | `concept_store.py` schema + migration | Small |
| Change `mark_stale_batch` to set `valid_to` instead of `stale=1` | `concept_store.py`, `observation_store.py` | Small |
| Add `as_of` parameter to queries | `concept_store.py:list_concepts()`, `search()` | Medium |
| Expose temporal query in MCP | `mcp_tools.py:prep_concepts` — add `as_of` parameter | Small |
| Remove destructive `prune_stale()` | `concept_store.py` — replace with archival | Small |

### Migration Path
```sql
ALTER TABLE concepts ADD COLUMN valid_from REAL;  -- epoch timestamp
ALTER TABLE concepts ADD COLUMN valid_to REAL;    -- NULL = currently valid
-- Backfill: valid_from = created_at for existing rows
UPDATE concepts SET valid_from = created_at WHERE valid_from IS NULL;
-- Stale concepts: valid_to = updated_at (when they were marked stale)
UPDATE concepts SET valid_to = updated_at WHERE stale = 1;
```

The `stale` column can be kept as a computed convenience (`valid_to IS NOT NULL AND valid_to <= now`) or removed after migration.

### Expected Impact
- **Historical recall**: "What did we believe about this module 3 months ago?" becomes answerable
- **Audit trail**: No knowledge is ever destroyed, only superseded
- **Better staleness semantics**: Instead of "this is stale", we know "this was valid from X to Y because Z"

### Risks
- Storage growth: negligible (concepts are small text, we're talking hundreds not millions)
- Query complexity: `as_of` filter is a simple WHERE clause addition
- Migration: SQLite ALTER TABLE ADD COLUMN is safe and fast

### Verdict: **DO THIS** — Medium priority, low effort, prevents knowledge loss

## Patterns to Skip

### 1. ChromaDB / Vector Store for Observations
MemPalace stores everything in ChromaDB for semantic similarity search. Prep uses SQLite + FTS5 for observations/concepts. **Don't switch.** Prep already has embedding-based search via `CodeIndex` for code chunks. Observations and concepts are small enough that FTS5 is sufficient, and adding a ChromaDB dependency for non-code knowledge would complicate deployment.

### 2. Entity Detection / Room Classification
MemPalace's `entity_detector.py` and `room_detector_local.py` classify content into people/projects/rooms. Prep doesn't need this — its entities are code symbols (functions, classes, modules), already identified by the Rust parser. The classification taxonomy is completely different.

---

## Patterns Worth Watching (Not Now)

### Duplicate Detection via Cosine Similarity
MemPalace checks cosine similarity >= 0.9 before filing new content. Prep uses exact content match for observation dedup. A semantic dedup could catch near-duplicate observations (e.g., "auth module is complex" vs "the authentication module has high complexity"). **Worth doing later** when observation volume grows, but not urgent.

### Protocol-as-Content
MemPalace embeds `PALACE_PROTOCOL` and `AAAK_SPEC` in every status response, teaching the AI how to use the tool on first contact. Prep already does this via the atlas section in `prep` responses. Worth studying MemPalace's phrasing for ideas on making Prep's self-documentation more effective. Not an implementation task.

|---------|--------------------|-----------------------|------|----------|---------|

| Private observation filtering (Track B) | Medium — agent continuity | Small | Low | 4 | **DO** |

---

## Implementation Order

1. **L2 Module-Scoped Retrieval** — Smallest change, biggest immediate impact on context quality
2. **Temporal Validity on Concepts** — Small schema change, prevents irreversible knowledge loss
3. **Structural Compression** — Requires more design but pays off at scale in swarm operations
4. **Private Observation Filtering** — Verify existing `visibility`/`created_by` fields are actually enforced in queries
