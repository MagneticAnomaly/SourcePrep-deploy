## 1. Executive Summary

The Master Architecture Diagram is a new interactive feature for the CoDRAG dashboard that provides a **visual, navigable, editable representation** of a codebase's architectural structure. It is not a static image or a read-only graph — it is a **living document** that serves three roles simultaneously:

1. **The Source of Truth** — The canonical representation of how the codebase is structured. When any AI agent asks CoDRAG "how does this codebase work?", the answer comes from this diagram. User edits, annotations, and architectural decisions override auto-generated data.

2. **A Navigation Interface** — A layered, drill-down interface where users can start from a high-level "system overview" showing major modules, click into any module to see its sub-architecture, and continue drilling down to individual files. Think Google Maps for code architecture.

3. **A Governance Surface** — A collaborative workspace where the user (acting as "the Board"), the Researcher agent, the CTO agent, and Backend Dev agents can communicate about architectural changes through formal Architecture Change Requests (ACRs), issue links, and annotations.

The diagram is built using **React Flow** (`@xyflow/react` v12), leverages **ELK.js** for automatic hierarchical layout, and integrates with CoDRAG's existing trace graph, module synthesis, and atlas systems. No new analysis pipeline is needed — the diagram is a read-only aggregation layer over existing data, augmented by user customizations persisted to the project's index directory.

## 2. The Problem

### 2.1 CoDRAG knows more than it can show

CoDRAG's pipeline already generates deep architectural understanding of a codebase:

- **Module Synthesis** (Stage 7) clusters files into logical modules with names and descriptions
- **Atlas Generation** (Stage 8) produces an LLM-written architectural overview
- **Trace Graph** (Stages 1-3) maps every import, call, and structural edge between files and symbols
- **Audit System** identifies architecture issues, tech debt, and improvement opportunities
- **Hub Files** analysis identifies the most-connected files in the codebase

But all of this intelligence exists as **text and raw data**. There's no visual representation. The Atlas is a wall of text. Module synthesis results are JSON blobs. The trace graph is a JSONL file with thousands of edges. A developer looking at the dashboard today can read the Atlas card and browse the Code Graph Explorer, but they can't see the big picture — how modules relate, where the bottlenecks are, which areas are clean and which are troubled.

### 2.2 The Atlas is auto-generated, not user-curated

The Atlas is generated by an LLM. It's a good starting point, but it's not the ground truth. The LLM doesn't know that:

- The "Auth" module is being migrated from JWT to OAuth2 next quarter
- The "Core" module was supposed to be split into "Core" and "Utils" six months ago but nobody's done it yet
- The "Legacy API" module should be deprecated and replaced by the new REST endpoints
- The team decided last Tuesday that all new database access should go through the ORM layer

These are **architectural decisions** that live in people's heads, in Slack messages, in meeting notes. They should live in CoDRAG — attached to the actual modules and files they affect — so that when an AI agent works on the codebase, it knows about them.

### 2.3 Agents work without architectural context

When a Paperclip agent picks up a task, it gets a scoped context from CoDRAG via the MCP tools. But that context is focused on specific files and search results. The agent doesn't get the big picture:

- "You're working in the Auth module. It depends on DB and Core. There's an active migration from JWT to OAuth2. Don't add new JWT code."
- "The Researcher identified 3 architecture issues in this module last week. Here they are."
- "The user approved ACR-42 which restructures this area. Here's the plan."

Without this context, agents make locally correct but globally wrong decisions. They might add more JWT code because they don't know about the migration. They might create a new direct database call because they don't know about the ORM decision.

### 2.4 No governance workflow for architectural changes

Currently, when the Researcher agent identifies an architecture issue (e.g., "this module has too many responsibilities"), there's no structured way to:

1. Propose a change to the architecture
2. Have the user review and approve it
3. Generate implementation tasks from the approved change
4. Track progress of those tasks back to the architectural goal
5. Verify the change was completed correctly

Issues go into Paperclip as standalone tickets. They lose their architectural context. There's no way to see "we planned to split this module into three, we've done two of the splits, one is still pending."

## 3. The Solution

The Master Architecture Diagram addresses all four problems with a single feature:

### 3.1 Visual representation of CoDRAG's architectural knowledge

The diagram takes CoDRAG's existing module synthesis, trace graph, and atlas data and renders it as an interactive graph. Modules become draggable rectangular nodes. Dependencies become directed arrows. Hub files glow. Entry points are diamonds. It's a flowchart — the industry-standard visual language for system architecture — but one that's alive, interactive, and always up-to-date with the codebase.

### 3.2 User curation with persistence

Users can:
- **Drag nodes** to arrange the diagram how they think about the architecture
- **Rename modules** if the auto-generated names aren't right
- **Add sticky-note annotations** with architectural decisions, migration notes, or warnings
- **Move files between modules** if the clustering isn't right
- **Mark entry points** and key interfaces

All changes persist. The next time the user opens the dashboard, the diagram looks exactly how they left it. And critically — their edits **override** the auto-generated data. If the user moves a file from Module A to Module B, that's the ground truth now, even if the LLM clusters it differently.

### 3.3 Agent context through MCP

When agents call the `codrag` MCP tool, the response includes the user-curated architecture:

```
## Architecture (user-curated)
8 modules: Auth (12 files, P1 migration active), API (24 files), Core (31 files)...
Auth → API: 15 imports | API → DB: 8 imports | Core → *: hub module

📌 ADR: "Migrating Auth from JWT to OAuth2 in Q2. See RFC-003."
📌 ADR: "DB module frozen — no new tables until schema audit."
⚠️ ACR-42: "Split Core into Core + Utils" (approved, in progress)
```

This means every agent automatically gets architectural awareness. The CTO agent knows about the OAuth2 migration. The Backend Dev agent knows not to add new tables. The Custodian agent knows that splitting Core is in progress.

### 3.4 Governance through Architecture Change Requests

The diagram introduces a formal **Architecture Change Request (ACR)** workflow:

1. **Anyone can propose** — The Researcher agent spots a circular dependency and creates ACR-43. A Backend Dev agent realizes during implementation that a module should be split and creates ACR-44. The user notices a missing abstraction layer and creates ACR-45.

2. **The user approves** — ACRs appear as warning badges (⚠️) on the affected diagram nodes. The user reviews them in the sidebar, reads the rationale, and approves or rejects.

3. **Approval creates tasks** — When the user approves an ACR, it automatically creates a linked Paperclip issue (or set of issues). The CTO agent can then design the implementation plan.

4. **Issues are visible on the diagram** — Each module/file node shows how many linked Paperclip issues it has. You can see at a glance which areas of the codebase have active work and which are clean.

5. **Completion updates the diagram** — When the pipeline re-runs after the code changes, the module synthesis detects the new structure, and the diagram updates to reflect reality.

## 4. Why This Matters

### For the solo developer

You get a visual map of your codebase that you can annotate with your own knowledge. Instead of keeping architectural decisions in your head, you put them on the diagram. When you come back to the project after a month, the diagram reminds you what you were doing, what you decided, and why.

When you ask an AI for help, it gets your architectural context automatically. No need to manually explain "we're in the middle of migrating from X to Y" — the AI already knows because it read the annotation on the diagram.

### For the team with AI agents

The diagram becomes the communication layer between the "board" (user/team lead), the analyst (Researcher agent), the architect (CTO agent), and the builders (Backend Dev agents). Everyone sees the same architectural view. Changes are proposed formally, reviewed visually, and tracked through completion.

It's like having a whiteboard that the whole team (humans and AI) can see, annotate, and reference — but one that's automatically kept in sync with the actual codebase.

### For CoDRAG's epistemic model

The Architecture Map is the missing piece in CoDRAG's knowledge stack:

```
Layer 1: Raw code           (trace graph — files, symbols, edges)
Layer 2: Semantic meaning   (augmentation — what each file does)  
Layer 3: Structural groups  (module synthesis — how files cluster)
Layer 4: Narrative overview (atlas — textual summary)
Layer 5: Curated truth      ← NEW: Architecture Map (user-verified structure + decisions)
```

Layer 5 is the highest-fidelity knowledge CoDRAG can have, because it's verified by a human. It's not inferred by an LLM — it's confirmed. When there's a conflict between what the LLM infers and what the user has curated, the user wins.

## 5. Core Concepts

### 5.1 Architecture Node

A visual element on the diagram representing a meaningful unit of code:

| Node Type | Shape | Represents | Examples |
|:---|:---|:---|:---|
| **Module** | Rounded rectangle | A logical grouping of related code | "Auth", "API", "Database" |
| **File** | Pill/capsule | A single source file | `login.py`, `schema.ts` |
| **Entry Point** | Diamond | An external-facing surface | API route, CLI command, main() |
| **External Ref** | Dashed rectangle | A module from another part of the tree | Shown when viewing a module that imports from outside |

### 5.2 Architecture Edge

A directed connection between nodes:

| Edge Type | Style | Represents |
|:---|:---|:---|
| **Import** | Solid arrow → | Static import dependency |
| **Call** | Dashed arrow ··→ | Runtime function call |
| **Inferred** | Dotted arrow ···→ | LLM-guessed relationship (from Stage 2) |
| **Aggregated** | Thick arrow + count | Bundled edges between modules ("12 imports") |

### 5.3 Architecture Annotation

A user or agent note attached to a node:

| Annotation Type | Author | Purpose |
|:---|:---|:---|
| **ADR** (Architecture Decision Record) | User | Formal architectural decision: "We're migrating to OAuth2" |
| **Comment** | User | Informal note: "This is messy, needs cleanup" |
| **Agent Note** | Researcher/Custodian | AI-generated observation: "Circular dependency detected" |

### 5.4 Architecture Change Request (ACR)

A formal proposal to change the architecture:

| Field | Description |
|:---|:---|
| **Source** | Who proposed it (user, researcher, backend dev, custodian) |
| **Affected Nodes** | Which modules/files are impacted (highlighted on diagram) |
| **Status** | Proposed → Approved → In Progress → Completed (or Rejected) |
| **Linked Issues** | Paperclip issues created when approved |

### 5.5 Layer

An abstraction level in the drill-down hierarchy:

| Layer | Shows | When You're Here |
|:---|:---|:---|
| **Layer 0: System** | All top-level modules, aggregated edges | Default view, the big picture |
| **Layer 1: Module** | Sub-groups within a module, file clusters | You clicked into a module |
| **Layer 2: Files** | Individual files, direct import/call edges | You drilled into a sub-group |
| **Layer 3: Symbols** (Future) | Functions/classes, call graph | You clicked a file |

### Key Navigation Rules

1. **Breadcrumb is always visible** — Shows the full path from system root to current layer. Click any segment to jump directly to that level.

2. **Back button** — Goes up one layer. `Esc` key also works.

3. **External references** — When viewing inside a module, dependencies on other modules appear as dashed "external ref" nodes at the edge of the canvas. Clicking one navigates to that module's layer.

4. **Each layer has its own layout** — When you drag nodes at Layer 0 and then drill into a module at Layer 1, the Layer 1 view has its own saved positions. Going back to Layer 0 shows your original arrangement.

5. **Animated transitions** — Drilling in and out uses a smooth zoom/pan animation so users maintain spatial orientation.

## 8. Source of Truth — MCP Context Integration

### What "source of truth" means

When we say the Architecture Map is the "source of truth," we mean:

1. **User edits override auto-generated data.** If the LLM clusters `utils.py` into the "Core" module but the user drags it to "Helpers", CoDRAG treats it as part of "Helpers" from that point forward — in MCP responses, in agent briefings, everywhere.

2. **Annotations become AI context.** If the user writes "Don't add new JWT code — we're migrating to OAuth2" on the Auth module, every agent that works on Auth-related files will see that warning in their CoDRAG context.

3. **The diagram's structure is the canonical module map.** The Atlas text is a derivative — it's generated *from* the architecture map data (once curated), not the other way around.

### How it integrates with MCP

The `codrag` MCP tool (the main tool AI assistants call at the start of every task) already returns ambient context including the Atlas text, hub files, and module structure. With Phase 71, it will also include the **architecture map context**:

```python
# In tool_context() — what the AI assistant sees:

## CoDRAG Context (42 chunks, 8400 chars)
Hubs: 5 | Modules: 8 | Neighbors: 12

### Architecture (user-curated, last updated 2026-04-01)

SYSTEM: 8 modules, 245 files, 1200 edges

MODULES:
- Auth (12 files) → depends on: DB, Core. Hub: login.py
  📌 "Migrating from JWT to OAuth2 in Q2. See RFC-003."
  ⚠️ ACR-42: "Add OAuth2 middleware layer" (approved, in-progress)
  🎫 3 open issues

- API (24 files) → depends on: Auth, DB, Core. Hub: routers/__init__.py
  ✅ clean

- Core (31 files) → depends on: DB. Hub: trace/index.py
  ⚠️ ACR-43: "Split Core into Core + Utils" (proposed)
  📌 "Core is intentionally large — it's the shared foundation."

- DB (8 files) → no dependencies. Hub: connection.py
  📌 "Frozen: no new tables until schema audit complete."

[... remaining context ...]
```

This gives the AI:
- **Module awareness** — knows which module each file belongs to
- **Dependency direction** — knows which modules depend on which
- **User decisions** — knows about migrations, freezes, and architectural rules
- **Active work** — knows about pending ACRs and open issues
- **Hub awareness** — knows which files are architecturally critical

### The priority chain

When assembling context for an AI, CoDRAG uses this priority:

```
1. Architecture Map annotations (highest — user verified)
2. Architecture Map module structure (user curated)  
3. Module synthesis results (LLM generated)
4. Atlas text (LLM summarized)
5. Raw trace graph data (lowest — structural only)
```

If the architecture map has been curated, it replaces the raw module synthesis and atlas sections in the MCP response. If it hasn't been curated (new project, user hasn't opened the panel yet), the system falls back to the auto-generated atlas as it does today.

## 9. Agent Governance — The Architecture Change Request Workflow

### The problem this solves

In a Paperclip-managed agent workforce, multiple agents work on the same codebase:

- The **Researcher** scans audit findings and proposes improvements
- The **CTO/Lead Dev** designs implementation plans
- **Backend Devs** write code
- The **Digital Custodian** cleans up dead code

Without coordination, these agents can make conflicting architectural decisions. The Researcher might propose splitting a module while a Backend Dev is adding to it. The Custodian might flag files as dead code that the CTO planned to refactor.

### The ACR workflow

Architecture Change Requests (ACRs) provide a structured governance process:

```
Step 1: PROPOSE
───────────────
Anyone (agent or user) creates an ACR:

  ACR-42: "Add OAuth2 middleware layer to Auth module"
  Source: Researcher Agent
  Affected Nodes: [Auth, API]
  Rationale: "Current JWT implementation has 3 P1 vulnerabilities.
              OAuth2 eliminates these and adds SSO support."

The ACR appears as a ⚠️ badge on the affected diagram nodes.

Step 2: REVIEW
──────────────
The user sees ⚠️ on the Auth module, clicks to open the sidebar,
and reads the ACR details:

  - What's proposed
  - Why (rationale from Researcher + link to audit findings)
  - Which files/modules are affected (highlighted on canvas)
  - Estimated effort

Step 3: DECIDE
──────────────
The user either:
  ✅ APPROVES — ACR status → "approved"
     → Automatically creates Paperclip issue(s)
     → Issue(s) linked to the diagram nodes
     → CTO agent can now design the implementation plan
     
  ❌ REJECTS — ACR status → "rejected"
     → Badge removed from diagram
     → Rationale saved for history

Step 4: IMPLEMENT
─────────────────
After approval:
  - CTO agent receives the Paperclip issue with full architecture context
  - CTO designs implementation plan, creates sub-issues for Backend Devs
  - Backend Dev agents pick up sub-issues
  - Each issue carries a codrag:// address linking back to the diagram node
  - When agents call `codrag` from the affected area, they see the ACR context

Step 5: COMPLETE
────────────────
When the code changes are merged:
  - CoDRAG's watcher detects file changes
  - Pipeline re-runs module synthesis
  - Diagram auto-updates to reflect new structure
  - ACR status → "completed"
  - Issue badges update (closed issues no longer show as active)
```

### What agents see

When an agent picks up a Paperclip issue that's linked to a diagram node, they can call a special endpoint to get scoped architectural context:

```
GET /projects/{id}/architecture/node-context/mod_auth

Response:
{
  "module": "Auth",
  "description": "User authentication and session management",
  "files": ["login.py", "session.py", "jwt.py", "middleware.py", ...],
  "dependencies": [{"module": "DB", "edge_count": 8, "kinds": ["imports"]}],
  "dependents": [{"module": "API", "edge_count": 15, "kinds": ["imports", "calls"]}],
  "hub_files": [{"path": "login.py", "score": 15}],
  "annotations": [
    {"type": "adr", "content": "Migrating to OAuth2 in Q2", "author": "user"},
    {"type": "agent_note", "content": "3 P1 vulnerabilities in JWT impl", "author": "researcher"}
  ],
  "active_acrs": [
    {"id": "ACR-42", "title": "Add OAuth2 middleware", "status": "approved"}
  ],
  "open_issues": [
    {"title": "Migrate JWT to OAuth2", "priority": "P1", "assignee": "backend_dev"}
  ]
}
```

This gives the agent everything it needs to understand the architectural context of its work, without having to parse the entire codebase.

## 10. Paperclip Integration — Bidirectional Issue Linking

### Diagram → Paperclip

From the Architecture Map UI, users (or agents) can:

1. **Right-click a node → "Create Paperclip Task"**
   - Auto-generates title: "Refactor: {module_name}" or "{file_name}: {issue_description}"
   - Pre-fills description with architectural context (module description, dependencies, user notes)
   - Attaches a `codrag://` address: `codrag://{project_id}/ARCH-{node_id}`
   - Links the created issue back to the diagram node

2. **Link existing issue to node**
   - Select a node → sidebar → "Link Issue" → paste Paperclip issue ID
   - The issue badge appears on the node

3. **Approve ACR → auto-creates issues**
   - When user approves ACR-42, the system calls `PaperclipClient.push_issue()` with the ACR details
   - The created issue is automatically linked to the affected nodes

### Paperclip → Diagram

When a Paperclip agent picks up an issue that has a `codrag://ARCH-*` address:

1. Agent calls `GET /projects/{id}/opportunities/{item_id}/context` (existing endpoint)
2. If the address is architecture-linked, the response includes:
   - The node's current state in the diagram
   - Upstream/downstream dependencies
   - User annotations and ADRs
   - Related ACRs and other open issues
   - Ready-to-use MCP command for deeper investigation

This creates a **bidirectional link**: the diagram knows about issues, and issues know about the diagram.

### What this looks like on the diagram

```
┌─────────────────────────┐
│  📦 Auth Module          │

## 13. API Design

### Phase A Endpoints (Core)

```
GET  /projects/{id}/architecture/graph
     Query: layer_path (string, default "")
     Returns: nodes[], edges[], external_refs[], stats{}
     
GET  /projects/{id}/architecture/summary
     Returns: module_count, file_count, edge_count, note_count, acr_count, last_edited
     
GET  /projects/{id}/architecture/state
     Returns: Full persisted state (layouts, overrides, positions)
     
PUT  /projects/{id}/architecture/state
     Body: { layouts, module_overrides }
     Saves user position changes (debounced from frontend)
     
GET  /projects/{id}/architecture/notes
     Returns: ArchitectureNote[]

POST /projects/{id}/architecture/notes
     Body: { node_id, content, note_type, author, color }
     Returns: created ArchitectureNote

PUT  /projects/{id}/architecture/notes/{note_id}
     Body: { content, color }
     Returns: updated ArchitectureNote

DELETE /projects/{id}/architecture/notes/{note_id}
     Returns: { deleted: true }

GET  /projects/{id}/architecture/context
     Returns: { text: string } — user-curated architecture as structured text for MCP

GET  /projects/{id}/architecture/node-context/{node_id}
     Returns: Module/file details, deps, notes, issues — for agent consumption
```

### Phase B Endpoints (Paperclip Integration)

```
GET  /projects/{id}/architecture/acrs
     Returns: ACR[]

POST /projects/{id}/architecture/acrs
     Body: { title, description, source_type, source_agent, affected_nodes }
     Returns: created ACR

PUT  /projects/{id}/architecture/acrs/{acr_id}/approve
     Returns: ACR with paperclip_issue_id (auto-created)

PUT  /projects/{id}/architecture/acrs/{acr_id}/reject
     Returns: ACR with status=rejected

POST /projects/{id}/architecture/nodes/{node_id}/link-issue
     Body: { paperclip_issue_id, title, priority, status }
     Returns: { linked: true }

DELETE /projects/{id}/architecture/nodes/{node_id}/link-issue/{issue_id}
     Returns: { unlinked: true }

POST /projects/{id}/architecture/create-task
     Body: { node_id, title?, description? }
     Returns: { paperclip_issue_id, codrag_address }

POST /projects/{id}/architecture/briefing
     Body: { node_id, scope: "module" | "file" }
     Returns: { briefing: string } — structured text for agent system prompt

## 16. Technology Decisions

### Why React Flow (`@xyflow/react` v12)?

| Criterion | React Flow | react-force-graph | Custom D3 | Mermaid |
|:---|:---|:---|:---|:---|
| Interactive editing | ✅ Native | ❌ View only | 🟡 Manual | ❌ Static |
| Custom node components | ✅ Full React | ❌ Canvas-based | 🟡 SVG only | ❌ None |
| Drag and drop | ✅ Built-in | ❌ Camera only | 🟡 Manual | ❌ None |
| Subflows/grouping | ✅ parentId | ❌ None | 🟡 Manual | ❌ None |
| TypeScript | ✅ First-class | 🟡 Types exist | 🟡 @types/d3 | ✅ Types exist |
| Dark mode | ✅ CSS variables | 🟡 Manual styling | 🟡 Manual | 🟡 Theme config |
| State management | ✅ Zustand (internal) | ❌ None | ❌ None | ❌ None |
| Community | ✅ 20K+ GitHub stars | ✅ Popular | ✅ D3 ecosystem | ✅ Popular |

**Decision:** React Flow wins because this is an **editor**, not a visualization. Users need to drag, annotate, rearrange, and interact with nodes. React Flow's custom node system lets us build rich card-style nodes with React components (badges, tooltips, context menus), which is impossible with canvas-based renderers.

### Why ELK.js for auto-layout?

| Criterion | ELK.js | Dagre | d3-force |
|:---|:---|:---|:---|
| Hierarchical layout | ✅ Excellent | 🟡 Basic | ❌ No |
| Direction control | ✅ Top-down, left-right, etc. | 🟡 Limited | ❌ N/A |
| Module group support | ✅ Native compound nodes | ❌ No | ❌ No |
| Edge routing | ✅ Orthogonal, splines | 🟡 Basic | ❌ No routing |
| Performance | ✅ WebAssembly option | ✅ Fast | 🟡 N² for simulation |

**Decision:** ELK.js produces clean, professional-looking hierarchical layouts that respect parent-child relationships (module groups). This is exactly what we need for architectural diagrams. Dagre would work for simple cases but doesn't handle compound nodes (modules containing files).

### Why file-based persistence (not database)?

The architecture state is stored as JSON files in the project's index directory, not in a database. This is consistent with how CoDRAG stores all other project data (trace graph, atlas, audit findings, module synthesis). Benefits:

- **Zero configuration** — no database setup needed
- **Portable** — the entire CoDRAG project directory can be copied/backed up as files
- **Version-controllable** — architecture state can be committed to git alongside code
- **Embedded mode compatible** — works with `.prep/` directories inside project repos
